# 라우팅·인증·보안 경계 규칙

루트 AGENTS.md 의 절대 금지 패턴 중 **라우팅·인증·보안 경계 규칙** 영역. 표의 왼쪽은 금지, 오른쪽이 올바른 사용이다.

## TL;DR (5초 요약)

```text
1. 인증/리다이렉트 규칙 (engine-v1.47.0+)
2. 정적 확장자 라우트 / 자산 URL 생성
3. 라우트 캐시 안전성
4. 조건부로만 열리는 라우트군의 게이트 (디버그·개발 라우트)
5. 중첩 리소스 스코프 / 계층 무결성
```

> 원본: 이 규칙들은 2026-09-10 까지 루트 AGENTS.md 「CRITICAL RULES」 에 있었다. 제목·표는 그대로 옮겼고 앵커는 바뀌지 않았다. 색인: [docs/rules/README.md](README.md)

## 정적 확장자 라우트 / 자산 URL 생성

| 금지 | 올바른 사용 |
|------|------------|
| `Route::get('{id}/routes.json', ...)` (`.js`/`.mjs`/`.css`/`.json`/`.map`/`.xml` 단일 등록) | `Route::dualSuffix('{id}/routes', 'json', ...)` — 확장자 형태 + 확장자 없는 형태 동시 등록 |
| `Route::get('bundle.js', ...)` (접미사가 종류를 구분해 제거 불가) | `Route::dualSuffixSegment('bundle', 'js', ...)` (`bundle.js` + `bundle/js`) |
| `Route::get('assets/{id}/{path}', ...)` (와일드카드 자산) | `Route::dualAsset('assets/{id}', ...)` (`.../{path}` + `?file=` 쿼리) |
| 서버에서 `'/api/templates/assets/'.$id.'/'.$path` 문자열 조립 | `App\Support\AssetUrl::templateAsset($id, $path)` |
| 프론트에서 `` `/api/templates/${id}/routes.json` `` 템플릿 리터럴 조립 | `resources/js/core/support/assetUrl.ts` 의 `suffixed()` / `templateAsset()` 등 |

정규식 location 은 프리픽스 location 보다 먼저 매칭되므로, 정적 최적화 블록(`location ~* \.(js|css|json)$`)이 있는 서버에서는 확장자 붙은 동적 응답이 `try_files ... /index.php` 폴백 기회 없이 404 가 된다. 서버측 `AssetUrl` 과 프론트측 `assetUrl.ts` 는 동일 규칙을 공유하므로 한쪽만 바꾸면 그 자산만 404 가 된다. 상세: [routing.md](../backend/routing.md) "정적 확장자로 끝나는 동적 엔드포인트", [api/README.md](../backend/api/README.md) "자산 URL 이중 모드".

## 브라우저가 만드는 주소 — 하위 폴더 마운트

사이트는 문서 루트가 아니라 하위 폴더에 설치될 수 있다(`https://host/g7/`). 서버가 렌더한 주소는 `AssetUrl::basePrefix()` 로 접두사를 갖는데 **브라우저 안에서 만드는 주소**는 루트 상대다 — 같은 화면에서 두 규칙이 공존하면 요청·이동이 사이트 밖으로 나가고, 증상은 오류가 아니라 **버튼이 조용히 무반응**인 것이다(문서 루트에 다른 사이트가 있으면 그쪽 응답을 받는다).

| 금지 | 올바른 사용 |
|------|------------|
| 코어 JS 에서 `fetch('/api/…')` · 변수로 조립한 뒤 `fetch(url)` | `withBasePrefix()` 또는 `assetUrl.ts` 생성기(`suffixed`·`templateAsset`·`extensionBundle` 등) |
| 확장 JS 에서 `fetch('/api/…')` | 확장별 `apiUrl()` (코어 `G7Core.url.api` 위임 + 같은 SSoT 폴백) — 확장 번들은 별도 IIFE 라 `import` 가 불가능하다 |
| 브라우저가 그대로 여는 주소를 루트 상대로 (`location.href` 대입 · `location.assign/replace` · `window.open` · 외부 인증기관에 넘기는 복귀 주소) | 코어는 `withBasePrefix()`, 확장은 `sitePath()` — 라우터를 거치지 않으므로 접두사를 붙일 주체가 호출부밖에 없다 |
| 브라우저 주소(`location.pathname`)를 라우트 패턴과 **그대로** 대조 | 코어는 `stripBasePrefix()`, 확장은 `routePath()` 로 접두사를 **벗긴 뒤** 대조 — 라우트는 언제나 접두사 없이 등록되므로, 벗기지 않으면 하위 폴더 사이트에서 그 대조가 언제나 불일치라 전 주소가 「없는 페이지」가 되고 그 기능이 조용히 사라진다 |
| `history.pushState`/`replaceState` 의 **세 번째 인자**를 루트 상대로 | 그 값도 브라우저가 보는 주소다 — 코어는 `withBasePrefix()`, 확장은 `sitePath()`. 붙이지 않으면 주소창이 사이트 밖 경로로 바뀌고, 그 뒤의 새로고침·뒤로가기가 사이트를 벗어난다 |
| 화면 링크를 날 `<a href="/…">` 로 직접 작성 | 템플릿 `A` 컴포넌트를 쓴다 — 그 컴포넌트가 `sitePath()` 로 접두사를 붙인다. 붙이는 자리를 한 곳으로 모아야 새로 추가되는 링크가 다시 사각이 되지 않는다 |
| 확장 헬퍼 사본(`apiUrl.ts`)을 확장마다 다르게 유지 | 바이트 동일한 사본 — 갈리면 그 확장만 다른 규칙을 따르고, 다른 확장이 정상인 만큼 원인이 더 숨는다 |
| 크롤러·메일이 받는 **절대** 자산 주소를 `url()` 이나 `str_starts_with('http') ? : AssetUrl::absolute()` 로 조립 | `SiteUrl::absolute()`(봇 화면은 이를 위임하는 `SeoUrl`) — 사이트 주소(`APP_URL`) 기준으로 오리진을 붙이는 단일 지점이고, 하위 폴더 설치에서 이미 접두사가 붙은 경로에는 접두사를 다시 붙이지 않는다. `AssetUrl::siteAbsolute()` 는 `SiteUrl::absolute()` 에 위임하는 호환용 이름이다. `url()` 은 이미 접두사를 품은 값에 접두사를 **한 번 더** 실어 404 를 만들고, 순진한 3항식은 프로토콜 상대(`//host/x`)·상대 경로(`img.png`)·`data:` 를 오리진에 그대로 이어 붙인다. 붙일 대상이 같은 사이트 안의 상대 경로뿐이면 `AssetUrl::sitePath()` |
| 메일·알림·비밀번호 재설정 링크 · 결제/본인인증 복귀·통보 주소 · 사이트맵 색인·증분 색인 · 봇 데이터소스 호출 같은 **서버가 만드는 절대 주소**를 `config('app.url').'/…'` 나 `url('/…')` 로 조립 | `SiteUrl::absolute('/…')`, 회원이 브라우저로 여는 사용자 화면 주소는 `ScreenUrl` — 둘 다 요청 Host 로 폴백하지 않는다. `url()` 은 요청의 호스트·접두사를 실어 앞단 프록시 배치에서 사이트 밖을 가리키고 접두사를 품은 값에 접두사를 한 번 더 싣는다. `config('app.url').'/…'` 는 `APP_URL` 의 후행 슬래시를 그대로 실어 `https://host/g7//login` 을 만든다. 둘 다 오류 없이 깨진 링크로만 드러나고, 요청이 없는 문맥(큐·콘솔)에서는 재현조차 되지 않는다. `general.site_url` 은 저장 시 후행 슬래시를 걷어낸다 |

봇이 받는 **절대** 주소는 축이 하나 더 있다 — 오리진을 붙이는 자리에서 「이미 절대인가」를 호출부가 직접 판정하면, `http` 로 시작하는 한 형태만 알고 나머지가 전부 샌다. 그 판정은 `SiteUrl::absolute()` 한 곳이 소유하며(`AssetUrl::siteAbsolute()` 는 그 위임) 정적 검사가 코어와 번들 확장 전체를 본다. `AssetUrl::absolute()` **단독** 호출은 대상이 아니다 — 「오리진만 붙인다」는 계약에 의존하는 형제 소비처가 있다.

붙이는 쪽(요청·이동)과 벗기는 쪽(라우트 대조)은 **다른 방향**이다. 한쪽만 재는 회귀 테스트는 다른 쪽이 통째로 빠져도 초록이므로 양방향을 함께 잰다. 판정할 수 없는 형태(변수·표현식)는 그 줄 바로 위에 `// base-path:allow <사유>` 로 의도를 남긴다 — 외부 시스템(PG 등)이 내려준 절대 주소가 그 자리다.

> 상세: [g7core-api.md "주소 조립 (G7Core.url)"](../frontend/g7core-api.md)
> 자동 차단: `assetUrl.test.ts` 의 소스 계약 검사 — 모집단은 코어 + **번들 확장 전체**이고(모집단이 비면 초록이므로 모집단 자체도 잰다), 사본 동일성도 같은 파일이 잰다. 벗기는 쪽은 정적 검사가 확장 전수를 따로 본다 — 붙이는 쪽과 다른 방향이라 한 축만으로는 다른 쪽이 통째로 빠져도 초록이다

## 파일 서빙 응답 계약 — 링크 유무로 위험이 갈리지 않는다

`public/storage` 심볼릭 링크를 만들 수 없는 호스팅에서는 public 디스크 파일이 정적 경로(`/storage/…`) 대신 읽기 전용 서빙 라우트로 나간다. 그 통로는 **정적 서빙과 동등**해야 한다 — 어느 한쪽에만 있는 성질이 생기면 같은 사이트가 링크 유무에 따라 다르게 동작하고, 그 차이는 오류가 아니라 조용한 동작 차이로만 나타난다.

| 금지 | 올바른 사용 |
|------|------------|
| 버전(`?v=`) 없는 URL 의 응답에 `Cache-Control: immutable` | 기본값이 요청의 `?v=` 유무에서 **파생**된다(`fileResponse(..., immutable: null)`) — 버전 없는 URL 은 자동으로 `must-revalidate` 다. 명시 인자는 그 파생을 덮을 때만 쓴다(공개 스토리지는 `false` 고정). 같은 URL 의 내용이 교체되는 자산에 `immutable` 을 붙이면 교체한 파일이 만료 전까지 옛것으로 남는다. 첨부는 대상이 아니다 — URL 에 내용 해시가 들어가 내용이 바뀌면 주소도 바뀐다 |
| 확장자를 모르는 파일의 MIME 을 **내용 스니핑**으로 결정 | 확장자 표에 없으면 `application/octet-stream` 고정 — 스니핑은 HTML 형태 업로드물을 `text/html` 로 승격시켜 브라우저가 실행한다(정적 서빙은 미지 유형을 내려받기로 준다) |
| public 디스크 URL 을 `Storage::disk('public')->url()` 로 직접 조립 | `ResolvesPublicUrl` 경유 — 링크 가용 판정(`StorageLinkHelper::publicStorageLinkUsable()`)이 SSoT 이고, 화면은 서버가 준 URL 을 그대로 쓴다 |
| 링크 존재를 `is_link()` 로만 판정 | `StorageLinkHelper::isLinkOrJunction()` — Windows junction 은 `is_link()`·`is_dir()` 이 모두 false 라 그대로 통과하며, 그러면 같은 계약이 OS 에 따라 성립·불성립으로 갈린다 |
| 응답 본문을 바꾸면서 `ETag` 를 그대로 승계 | 표현이 다르면 다른 ETag (RFC 9110 §8.8.1) — gzip 본문은 `-gzip` 접미사를 붙이고, 재검증 비교는 그 접미사를 벗겨 판정한다 |
| `Vary: Accept-Encoding` 을 **압축한 응답에만** 부착 | 압축 대상 유형이면 압축 여부와 무관하게 부착 — 유무가 갈리면 공유 캐시가 잘못된 표현을 재사용한다 |
| HEAD·부분 응답(206)을 압축 경로에 태움 | 둘 다 제외 — `BinaryFileResponse` 를 일반 응답으로 치환하면 HEAD 에 본문이 실리고, 206 은 `Content-Range` 와 본문이 어긋난다 |
| 자산 서빙 경로를 요청 클래스마다 따로 흡수·검증 | `ResolvesDualModeFilePath` (입력 흡수) + `ValidatesExtensionAssetPath` (판정) 를 네 통로가 공유 — 사본이 갈리면 같은 파일이 통로마다 다른 판정을 받고, 실제로 한쪽에만 들어간 보강이 나머지에서 누락됐다 |
| 확장 자산 경로에 점(`.`)으로 시작하는 세그먼트를 허용 | 거부 — 서버 3종 설정의 숨김 파일 차단은 **URL 경로**에만 걸리는데 확장자 없는 모드는 그 경로를 `?file=` 로 옮겨 그 방어선을 지나간다. 공개 스토리지는 그 거부를 **404** 로 낸다(정적 서빙과 같은 코드) |
| 확장 자산 서빙 서비스가 요청 규칙만 믿고 경로를 그대로 열기 | `SecuresExtensionAssetPath` 로 2차 봉쇄(정제 + realpath 재확인) — 규칙 한 줄이 무력해지면 남는 방어선이 없다 |
| 확장 자산 서빙 **서비스** 중 일부만 확장자 화이트리스트 2차 확인 보유 | 세 서비스(module·plugin·template)가 같은 강도 — 한쪽만 있으면 컨트롤러의 `file_type_not_allowed` 403 분기가 나머지에서 **도달 불가**가 되고, 운영 소스맵 차단 같은 보강이 그 통로에서만 사문화된다. 「요청 규칙이 이미 막으니 무해하다」는 방어가 아니다 — 서비스는 확장에 열려 있다 |
| 확장 자산 MIME 표를 통로마다 사본으로 유지 | 공유 SSoT 경유 — 사본이 갈리면 같은 파일이 통로마다 다른 `Content-Type` 으로 나가고, `local` 소스맵 완화가 일부 통로에서만 성립한다 |
| `?file=` 값 인코더가 서버(`rawurlencode`)와 프론트(`encodeURIComponent`)로 갈림 | 양쪽이 같은 RFC 3986 규칙 — `!` `'` `(` `)` `*` 의 처리가 달라 같은 자산의 URL 문자열이 둘로 갈리면 HTTP 캐시 키가 분할된다(오류는 나지 않는다) |
| 노출 점검 sentinel 을 확장자 있는 이름·고정 권한으로 생성 | 확장자 없는 이름 + **같은 디렉토리 대조 파일과 같은 권한 등급** — 0600 으로 고정하면 정상 서버에서도 storage 계열이 상시 「측정 불가」가 되어 자동 차단이 모든 배치에서 운영자 확인으로 강등된다 |

**`api/*` 의 검증 실패는 `Accept` 헤더와 무관하게 언제나 JSON 422 다.** 프레임워크 기본값은 「JSON 을 기대하지 않는 요청이면 302 + 이전 주소로 되돌리기」인데, 자산 요청은 `Accept: image/*` 로 오므로 그 기본값이 그대로 걸린다 — 그러면 잘못된 경로 하나로 **무인증 오픈 리다이렉트**가 성립하고(되돌릴 주소는 `Referer` 다), 같은 파일을 내주는 정적 서빙(404)과 응답 형태도 갈린다. 새 API 경로는 이 계약을 전제로 쓴다.

| 금지 | 올바른 사용 |
|------|------------|
| `api/*` 응답 형태를 `expectsJson()` 으로 분기 | 전 경로 JSON 고정 — 분기는 `bootstrap/app.php` 의 렌더러 한 곳이 소유한다 |
| 코어 업데이트가 루트 보호 파일 갱신 결과(`RootHtaccessUpdater::apply()`)를 버림 | `isFailure()` → `failureMessage()`, 실패가 아니어도 `noticeMessage()` — 「마커가 없어 갱신하지 않았다」는 **보호 규칙이 미적용으로 남았다**는 뜻이라 조용히 넘기면 안 된다 |
| 롤백 경로만 경고 통로에서 빠뜨림 | 업데이트·롤백 **양쪽**이 같은 통로로 출력 — 한쪽만 배선하면 그 경로의 사실이 로그 파일에만 남는다 |
| `deploy/**` 서버 설정 조각을 디렉토리 통째 복사로 갱신 | `CoreUpdateService::applyDeployFragments()` — 조각 머리말이 운영자에게 직접 수정을 지시하므로, 수정본은 보존하고 새 판본을 `<이름>.dist` 로 옆에 두고 경고한다. 판정 근거는 백업이 아니라 **코어가 마지막으로 제시한 판본의 해시 원장**(`storage/app/core-update/deploy-fragments.json`)이다 — 백업은 현재 디스크의 사본이라 「운영자가 고쳤는가」를 말해 주지 못한다. **보존한 조각도 원장에 새 판본의 해시를 기록한다** — 기록하지 않으면 운영자가 `.dist` 를 합친 뒤에도 매 업데이트마다 「판정 불가 → `.dist`」 가 반복된다. 원장이 없는 설치본은 `seedDeployFragmentLedger()`(인스톨러·업그레이드 스텝)가 사이드카 없는 조각의 디스크 해시로 씨앗한다. 옛 `.dist` 가 새 판본과 다르면 덮어쓰지 않고 `.dist.new` 로 둔다(합치던 중간 작업 보호). 원장 쓰기 실패는 통보 통로에 싣는다. 롤백은 `.dist`·`.dist.new` 와 원장을 함께 걷는다 |
| 루트 `web.config` 를 「코어 소유, 통째 교체」로 갱신 | 루트 `.htaccess` 와 **같은 마커 블록 규칙** — `BEGIN G7`/`END G7` 을 담은 XML 주석 줄이 경계이고 블록(`system.webServer` 전체)만 교체한다. 판정 로직은 `AbstractRootMarkerFileUpdater` 하나가 소유하고 자식은 마커·문구 키만 정한다(사본 금지). 어느 루트 파일이 갱신기를 지나는지는 리터럴이 아니라 `CoreBackupHelper::ROOT_MARKER_FILE_UPDATERS` 에서 도출하며, 정상 targets 분기와 자동 발견 폴백 분기 **둘 다** 그 표를 본다 |
| 정적 서빙에 `X-Content-Type-Options: nosniff` 부재 | 네 서버 설정 전부에 둔다 — `public/.htaccess`(`Header always set`, `mod_headers` 가드 · FileInfo 등급)·`web.config`(`customHeaders`)·nginx(`add_header … always`)·Caddy(`header`). 앱의 파일 응답 헬퍼가 같은 헤더를 붙이므로, 정적 서빙에 없으면 `public/storage` 링크 유무에 따라 업로드된 SVG·HTML 의 실행 여부가 갈린다. nginx 의 `add_header` 는 상속되지 않고 **대체**되므로 서버 수준 헤더는 조각 안에 함께 적는다 |
| 루트 `.htaccess` 갱신의 임시 파일을 **링크가 놓인** 디렉토리에 생성 | 링크 **대상**의 디렉토리(`resolveWriteTarget()`) — 대상이 다른 파일시스템이면 `rename()` 이 EXDEV 로 실패해 보호 규칙이 구판으로 고착되고, 안내는 권한만 가리킨다 |
| `applyUpdate()`/`restoreFromBackup()` 반환값을 버리고 `getLastRootFileWarnings()` 게터에만 의존 | 반환값의 `root_file_warnings` 가 계약이다 — 게터는 콘솔 커맨드의 편의이고, 커맨드가 아닌 소비처(웹 워커)는 반환값으로만 그 사실을 받는다 |

`ETag` 는 큰따옴표로 감싼다(RFC 9110 §8.8.3). 따옴표 없는 값은 유효한 entity-tag 가 아니라 중간 프록시·CDN 이 버리거나 다시 쓸 수 있고, 정적 서빙은 언제나 따옴표를 붙인다. `Last-Modified` 를 내보내면 `If-Modified-Since` 도 함께 처리한다 — 내보내기만 하고 무시하면 ETag 를 쓰지 않는 프록시가 매번 전문을 받아 간다.

**재검증 비교는 한 지점이 소유한다.** 압축본은 표현이 다르므로 ETag 에 `-gzip` 접미사가 붙는데, 비교하는 쪽이 그 접미사(그리고 다중값·`W/` 약한 검증자)를 흡수하지 않으면 브라우저가 돌려보낸 값이 **영원히 불일치**해 그 URL 의 304 가 통째로 사라진다. 오류도 경고도 없이 매 재검증이 전문 200 이 되는 형태라, 회귀 테스트는 반드시 `Accept-Encoding: gzip` 을 실은 **2왕복**이어야 한다 — 그 헤더가 없으면 압축이 일어나지 않아 접미사도 붙지 않고, 엄격 비교로도 통과한다.

**304 는 200 이 실었을 헤더를 함께 싣는다** — `Cache-Control`·`Expires`·`Vary`(RFC 9110 §15.4.5). `Vary` 가 빠지면 공유 캐시가 어떤 축으로 갈린 표현인지 모른 채 항목을 갱신한다. 다만 200 이 싣지 않는 축을 304 에만 붙이지 않는다(반대 방향 비대칭).

| 금지 | 올바른 사용 |
|------|------------|
| `If-None-Match` 를 `===` 로 직접 비교 | 비교 헬퍼 단일 지점 경유 — 접미사·다중값·`W/` 를 그 한 곳이 흡수한다 |
| 무인증·무상한 파일 서빙 경로를 압축 미들웨어에 태움 | 압축은 웹서버·CDN 의 몫 — 그 경로는 압축에서 명시적으로 제외한다(압축 경로는 파일을 통째로 메모리에 읽어 동시 요청 수만큼 증폭된다). 판정 근거는 **크기의 유계성**이다: 상한(`MAX_FILE_COMPRESS_SIZE`) 안에서 크기가 유계인 배포 자산(코어·확장 번들·템플릿 자산)은 압축 대상이고, **사용자가 올린 파일**처럼 크기·건수가 유계가 아닌 통로만 제외한다. 형제 공개 자산 라우트가 제외 선언을 갖지 않는 것은 누락이 아니라 이 판정의 결과다 |
| 스트림 서빙 헬퍼에만 `immutable` 인자를 두지 않음 | 형제 헬퍼와 같은 인자 — 없으면 그 경로의 소비처는 위 `immutable` 규정을 지킬 수단이 없다 |
| 압축본이 `Accept-Ranges: bytes` 를 승계 | 압축하면 그 헤더를 **제거**한다 — 그 오프셋은 identity 표현의 것인데 같은 URL 에 `Range` 가 오면 206 이 압축에서 제외돼 identity 로 나가므로, 압축본 길이로 범위를 계산한 재개 다운로드가 다른 표현을 이어붙인다. 정적 서빙은 압축 시 이 헤더를 지운다 |
| 304 가 identity ETag 를 싣는데 같은 요청의 200 은 `-gzip` 을 싣기 | 304 는 **클라이언트가 보유한 표현**의 검증자를 그대로 돌려준다 — 접미사는 본문 있는 응답에만 붙어 304 는 압축 경로를 지나지 않는다. 어긋나면 공유 캐시가 gzip 본문을 identity 검증자로 갱신해, 200 에서 표현을 갈라 놓은 이유가 그 자리에서 사라진다 |
| 무확장자 자산 URL 모드의 응답이 **파일 이름**을 선언하지 않음 | 파일 응답 헬퍼 단일 지점이 `Content-Disposition: inline; filename=…` 을 붙인다 — 그 모드에서는 URL 마지막 세그먼트가 확장 식별자라, 선언이 없으면 같은 파일이 URL 모드에 따라 다른 이름으로 저장되고 정적 서빙과도 갈린다. 호출부로 내리면 통로마다 갈린다 |
| 공개 디스크 URL 전환을 링크 판정만으로 결정 | 운영자가 그 디스크 URL 을 다른 위치로 지정했으면 그 설정이 우선 — 링크 부재를 이유로 로컬 라우트로 끌어오면 그 사이트의 공개 자산이 통째로 어긋난다 |
| 파일 서빙 응답에 `X-Content-Type-Options: nosniff` 부재 | 헬퍼 단일 지점(`fileResponse()`·`streamedFileResponse()`)이 200·304 모두에 붙인다 — 업로드된 SVG·HTML 이 앱 오리진에서 실행되는 축이다. 정적 서빙 설정은 그 헤더를 붙이므로 이 통로만 빠지면 링크 유무로 위험이 갈린다. 호출부로 내리면 열 통로 중 하나가 반드시 빠진다 |
| 컨트롤러가 스토리지 스트림·`response()->file()` 을 **그대로** 돌려줌 | 파일 응답을 돌려주는 컨트롤러 메서드는 전부 헬퍼 두 지점 중 하나를 지난다 — 응답 계약(nosniff·ETag·304·압축 제외 선언)은 그 지점에만 있고, 지나지 않는 통로는 오류 없이 헤더만 빠진다 |
| 스트림 헬퍼에 사용자 업로드물을 넘기면서 `immutable`·`mimeType`·`skipCompression` 을 생략 | 셋 다 명시 — 생략은 오류가 아니다: `immutable` 은 요청자가 붙인 `?v=` 로 파생돼 업로드물이 1년 불변이 되고, `mimeType` 은 어댑터 추정(사본)에 기대며, 압축 제외는 응답 클래스를 보고 건너뛰는 우연이 된다 |
| 빈 문자열 MIME 을 「모름」과 다르게 취급 (`??=` 로 `null` 만 폴백) · 어느 쪽도 비면 예외 | `''`·공백도 응답 헤더로 폴백하고, **어느 쪽도 비면 `application/octet-stream`**(정적 서빙의 미지 유형 규약 — 알 수 없으면 내려받기, 스니핑 금지). 예외로 던지면 행 `mime_type` 이 빈 첨부(데이터 상태)가 무인증 표면의 500 이 된다 |
| 서비스가 돌려준 서빙 메타(`response`·`etag_source`·`mime_type`·`last_modified`)의 키 검증을 컨트롤러마다 `array_key_exists` 사본으로 | `streamedFileResponseFromMeta()` 단일 지점(`FileServingMeta` 값 객체) — 사본은 두 곳에만 있었고 나머지 아홉 통로는 무가드라 서비스가 키를 빠뜨리면 500 또는 조용한 축 소실이었다. 컨트롤러별 `servedWithCacheContract()` 사본도 두지 않는다 |
| 실재하지만 읽을 수 없는 파일을 파일 응답에 그대로 넘김 | 정적 서빙과 같은 **403** — 넘기면 `File must be readable` 예외로 무인증 표면이 500 + 스택 로그다. 판정은 서비스(`isReadable()`)가 소유해 `chmod` 로 재현할 수 없는 환경에서도 잠근다 |
| `Accept-Encoding` 을 `str_contains('gzip')` 으로 판정 | RFC 9110 §12.5.3 가중치 — `gzip;q=0` 은 명시 거부라 압축하지 않고, `*` 는 gzip 이 따로 거부되지 않은 한 압축한다 |

**HEAD 는 압축하지 않는다** — 그 응답에는 본문이 없어야 하는데 압축 경로가 파일 응답을 일반 응답으로 치환하면서 본문을 싣기 때문이다. 그 결과 같은 URL 에 대해 HEAD 와 GET 이 서로 다른 표현을 광고한다(GET 은 `Content-Encoding: gzip` + 접미사 ETag, HEAD 는 둘 다 없음). 본문 없는 응답에서 그 차이는 무해하지만, HEAD 로 크기·검증자를 미리 재는 클라이언트는 GET 이 돌려줄 값과 다른 것을 본다는 사실을 전제해야 한다.


배포 레이아웃 ②(문서 루트 = 프로젝트 루트)의 루트 `.htaccess` 에서 `mod_rewrite` 부재 시 방어선이 막는 디렉토리·파일 목록은 **그 목록이 완전한지를 사람의 기억에 맡기지 않는다** — 기대값을 배포 대상(`update.targets`)과 실제 최상위 디렉토리·파일에서 도출해 계약 검사가 대조한다. 목록 자체는 `.htaccess` 에 그대로 적혀 있고(Apache 가 그 파일만 읽는다), 최상위 항목이 하나 늘면 그 검사가 red 가 돼 사람이 옮긴다. 손으로만 유지하던 시절에는 그 강제가 없어 두 차례 연속으로 불완전했다.

**배포 레이아웃 ②의 `.htaccess` 는 `Options`·`Require` 를 쓰지 않는다.** 두 지시어는 각각 `Options`·`AuthConfig` 등급의 `AllowOverride` 를 요구하는데, 저가형 공유 호스팅에서 흔한 `AllowOverride FileInfo Limit Indexes` 조합에는 그 등급이 없어 Apache 가 「not allowed here」로 **그 디렉토리 하위 전 요청을 500** 으로 만든다(실측). 모든 요청이 `public/` 으로 위임되는 배치에서 그 500 은 곧 사이트 전체 장애이고, 인스톨러조차 뜨지 않아 원인을 알려 줄 화면이 없다. `<IfModule>` 은 그 가드가 되지 않는다 — 모듈 **유무**만 보고 권한 등급은 보지 못하므로 감싼 채로도 500 이 난다(실측). 같은 보호를 등급이 낮은 수단으로 낸다: 경로 판정은 `RedirectMatch`(FileInfo), 접근 거부는 `Order`/`Deny`(Limit), 디렉토리 목록 차단은 `IndexIgnore`(Indexes).

| 금지 | 올바른 사용 |
|------|------------|
| 배포되는 `.htaccess` 에 `Options`(`-Indexes`·`-MultiViews` 포함)·`Require` | `IndexIgnore`·`RedirectMatch`·`Order`/`Deny` — 제한 `AllowOverride` 에서도 평가되는 등급으로 같은 보호를 낸다 |
| `<IfModule>` 로 감싸 등급 문제를 피했다고 간주 | 모듈 유무와 권한 등급은 다른 축 — 감싸도 500 은 그대로다 |
| 정본 주소·트레일링 슬래시 정규화를 **부모** 디렉토리 `.htaccess` 에 둠 | 규칙은 **평가되는 파일**이 소유한다 — mod_rewrite 의 디렉토리별 설정은 상속되지 않아, 자식이 `RewriteEngine On` 을 선언하면 그 요청에 대해 부모 규칙집이 통째로 대체된다(루트에 적은 `^public/…` 는 평가될 기회가 없고, 실측에서 `/public/favicon.ico` 가 301 이 아니라 200 으로 나갔다) |
| 정규화 규칙이 **위임된 내부 리다이렉트**까지 대상으로 삼음 | 브라우저가 직접 친 요청만 대상으로 한다(`REDIRECT_STATUS` 가 비어 있는 요청) — 위임된 요청까지 잡으면 위임 자체가 되던져져 무한 301 이 된다 |
| 정규화 응답에 `/public` 접두를 실어 돌려보냄 | 접두 없는 정본 주소로 돌려보낸다 — 실어 보내면 서버가 스스로 제2 주소 체계를 공표하고, 실존 최상위 디렉토리에서는 무한 301 이 된다 |
| 마운트 위치를 **파일시스템·문서 루트 조회**로 판정 (`%{DOCUMENT_ROOT}…/public/index.php -f`) | mod_rewrite 가 per-directory 규칙에 넘기는 **매치 문자열**로 판정한다 (`RewriteRule !^public/`) — 그 값은 URL 에서 이 디렉토리에 해당하는 앞부분이 이미 벗겨진 나머지라, 레이아웃 ②·하위 폴더·별칭에서는 `public/` 이 남지 않고 표준 배치에서는 남는다. `DOCUMENT_ROOT` 는 **웹서버의 `DocumentRoot` 지시어**이지 사이트가 놓인 위치가 아니어서, 운영자가 문서 루트 밖을 `Alias` 로 여는 배치에서는 조회가 빗나가 규칙이 통째로 꺼진다(실측: 별칭 대상이 문서 루트와 같으면 우연히 성립하고, 밖이면 `/g7out/public/…` 가 200) |
| 정본 주소 301(**직접 요청**)의 목적지를 `%{THE_REQUEST}`(요청 라인 원문)에서 만듦 | 서버가 **디코딩한 `%{REQUEST_URI}`** 에서 만든다 — 이 규칙은 직접 요청 전용(`REDIRECT_STATUS` 가 비어 있음)이라 위임으로 값이 다시 쓰이기 전이고, 그 시점의 `REQUEST_URI` 는 마운트 접두사를 그대로 갖는다. 원문에서 만들면 아래 행의 접두사 오인이 성립한다 |
| 슬래시 보정(**위임된 요청**)의 목적지를 `%{REQUEST_URI}` 에서 **재조립** | `%{THE_REQUEST}` 에서 만든다 — 별칭(`Alias`) 마운트 중 **별칭 대상이 그 vhost 의 `DocumentRoot` 와 같은 디렉토리**인 배치는 **위임된** 요청의 `REQUEST_URI` 가 접두사를 잃은 `/public/…` 라 재조립 `%1` 이 비어 결과가 **사이트 밖 주소**가 된다(7마운트 × 3형태 실측 — 별칭 3축 중 그 1축만 잃고, 대상이 문서 루트 **밖**이면 실린다. 「별칭이면 항상 잃는다」가 아니다). 판별자는 「별칭이냐」가 아니라 아래 `SCRIPT_NAME` 행과 **같다**. 접두사 소실은 위임된 요청에만 해당하므로 위 행에는 걸리지 않는다 |
| `NE` 를 붙일지를 규칙마다 감으로 정함 | **목적지를 어느 값에서 만들었는가**가 정한다 — `%{THE_REQUEST}`(인코딩된 원문)는 `NE` 필수(없으면 `%20` 이 `%2520` 으로 나간다), `%{REQUEST_URI}`(디코딩된 값)는 `NE` 금지(붙이면 반대로 인코딩이 모자라 공백·한글 주소가 깨진다). 한 방향만 재는 검사는 반대쪽 실수를 통과시킨다 |
| 사이트 위치를 **경로 세그먼트 이름**(`/public/`)으로 판정하면서 그 이름이 마운트 접두사에도 있을 수 있음을 무시 | 접두사에 같은 이름이 들어갈 수 있다(`Alias /my/public/site`) — 인코딩된 요청 원문에서 그 이름을 찾으면 **접두사 자신의 세그먼트**만 남아 그 자리를 사이트의 공개 폴더로 오인하고, 잘라 낸 결과가 **사이트 밖 주소로 301** 이 된다(실측: `/my/public/site/%70ublic/favicon.ico` → `Location: …/my/site/%70ublic/…`). 디코딩된 값은 두 세그먼트를 모두 보여 주고, 자를 자리는 **정규식 탐욕성이 아니라 per-directory 매치 문자열**(`$1`)에 묶어 고정한다 — 탐욕성으로 고르면 라우트 자신의 `public` 세그먼트가 목적지에서 삭제되고(실측 `/public/board/public/1` → `/board/1`), 레이아웃 게이트가 첫 세그먼트만 보므로 **표준 배치**(문서 루트 = `public/`)에서도 `public` 이 뒤에 든 주소가 깎인다(`/storage/public/img.png` → `/storage/img.png`) — 그 배치는 이 규칙이 관여하지 **말아야** 한다 |
| 위임 규칙이 **사이트 안 경로**(`E=G7_ROUTE:$1`)를 진입 스크립트에 넘기지 않음 | 넘긴다 — 별칭(`Alias`) 마운트 중 **별칭 대상이 그 vhost 의 `DocumentRoot` 와 같은 디렉토리**인 배치는 `SCRIPT_NAME` 이 `/public/index.php` 로 접두사를 잃는다(실측 — 대상이 문서 루트 **밖**이면 실린다. 「별칭이면 항상 없다」가 아니다). 그 배치에서 이 값이 없으면 진입 스크립트가 접두사를 복원할 근거를 잃고 미설치 안내가 사이트 밖으로 보낸다. 브라우저 주소만으로는 어디까지가 마운트인지 구분할 수 없으므로 **추정으로 메우지 않는다** |
| 공개 스토리지 서빙 루트로 `filesystems.disks.public.root` 값을 그대로 신뢰 | **로컬 드라이버 + 절대 경로**일 때만 신뢰하고, 아니면 `storage/app/public` 으로 폴백하며 그 사실을 경고로 남긴다 — 비로컬 디스크의 root 는 원격 버킷 접두사라 로컬 경로로 쓰면 서빙이 통째로 어긋난다 |
| 링크 가용 판정을 링크의 **존재**로만 결정 | 링크가 **설정된 루트**를 가리키는지까지 본다 — 운영자가 루트를 옮긴 사이트에서 옛 위치를 가리키는 살아 있는 링크는 가용으로 읽혀 URL 이 `/storage/…` 로 나가는데 그 트리는 비어 있어 공개 자산이 전부 조용히 404 가 된다(오류도 로그도 없다) |

> 상세: [api/system.md](../backend/api/system.md) · [storage-driver.md](../extension/storage-driver.md)

## 웹에서 도는 코어 업데이트 — 요청 경계가 곧 격리다

SSH 를 쓸 수 없는 호스팅의 코어 업데이트는 **한 요청이 한 단계**만 수행한다. 파일을 교체한
프로세스가 사라진 클래스를 참조하면 치명 오류가 나는데, 명령행은 그 격리를 `proc_open`
스폰으로 얻고 스폰이 막힌 호스팅에는 그 수단이 없다 — 요청 경계가 그것을 대신한다. 그래서
단계 분리는 편의가 아니라 **안전 요건**이고, 한 단계 안에서 둘을 이어 하면 목록은 그대로인
채 경계만 사라진다.

| 금지 | 올바른 사용 |
|------|------------|
| 한 단계 구현이 파일 적용과 업그레이드 스텝을 이어 수행 | 두 단계는 **다른 요청** — `CoreUpdateStep` 순서와 `stepApply`/`stepUpgradeSteps` 분리가 그 경계다 |
| 파일 적용 직후 같은 요청에서 `clearAllCaches()`·`package:discover` 호출 | 컴파일 캐시 **파일만 삭제** — 커맨드를 부르면 방금 교체된 파일을 구버전 프로세스가 로드한다 |
| 웹 착수 요청에 `force`·`prune`·`no_backup`·`no_maintenance` 입력을 두고 검증으로 거르기 | **입력 표면 자체를 두지 않는다** — 규칙 한 줄만 풀면 켜지는 값이 남으면 그 선언은 유지되지 않는다. 명령행의 그 옵션들은 그대로 유지한다(웹 미노출이지 기능 제거가 아니다) |
| 요청 경계를 넘는 직렬화를 `flock`(`acquireRunLock`)에 의존 | 잠금은 프로세스 수명에 묶여 요청 사이를 잇지 못한다 — 상태 파일의 **점유(토큰 + 심박)** 가 그 축이고, `flock` 은 동시에 도는 명령행 실행을 막는 데 쓴다 |
| 점유 심박을 읽지 못한 것을 「오래됨」으로 접어 회수 | 판정 불능은 **보유 중**(fail-closed) — 접으면 진행 중인 다른 요청의 점유를 빼앗아, 그 점유가 막으려던 상태가 그대로 재현된다 |
| 진행·되돌리기 엔드포인트를 유지보수 모드 면제 목록에서 누락 | 업데이트가 **스스로 켠** 점검 모드에 진행이 갇힌다 — 목록(`MaintenanceModePage::MAINTENANCE_EXEMPT_URIS`)과 실제 라우트 URI 가 어긋나면 진행이 오류 없이 503 으로 멈춘다 |
| 우회 쿠키만으로 관리자 화면 접근을 보장 | 쿠키는 만료·다른 기기·차단으로 없을 수 있다 — 면제 목록과 **둘 다** 둔다(한쪽은 복구 경로, 한쪽은 화면) |
| 실패를 화면에 「실패했다」로만 표시 | 운영자가 먼저 알아야 하는 것은 **「지금 사이트는 멀쩡한가」** — 되돌리기 결과를 실패 사유와 **분리된 영역**에 둔다 |
| 진행 중에 사람이 멈추는 버튼 제공 | 파일 교체 중 중단은 반쪽 상태를 남긴다 — 실패 판정과 되돌리기는 시스템이 한다 |
| 업그레이드 스텝 단계를 배포 기본값(`spawn_failure_mode=abort`)으로 그냥 돌리기 | 그 단계에서 **`fallback` 을 강제**한다 — 웹은 `.env` 의 `APP_VERSION` 이 마무리 단계까지 옛 값이라 stale 메모리 가드가 **항상** 참이 되고, 매 요청이 같은 핸드오프를 던져 상한까지 반복한 뒤 **정상 적용된 코어가 되돌려진다**. 그 가드의 전제(부모가 구버전 코드를 들고 있다)는 웹에서 성립하지 않는다 — 이 단계는 파일 적용 다음 요청이다. 강제 채널은 `config()`(in-process)와 `$_ENV`/`$_SERVER`(자식 프로세스)이며 `putenv` 는 쓰지 않는다(프로세스 수명에 남아 같은 워커의 다음 요청까지 모드를 바꾼다) |
| 되돌리기 경로를 성공 경로보다 약하게 마무리 | 되돌리기도 **파일을 쓰는 구간**이다 — 소유권·퍼미션 복원·컴파일 캐시 파일 삭제(커맨드 호출 금지)·단계 수행과 같은 잠금, 셋 다 성공 경로와 같은 강도로 적용한다. 파일만 제자리에 놓고 끝내면 되돌린 사이트가 쓰기 권한을 잃은 채 500 으로 뜬다 |
| 사전 진단을 실행 1단계에서만 수행 | 착수 화면이 **누르기 전에** 그 판정을 받는다 — 쓰기 권한이 없는 호스팅의 운영자가 사이트를 점검 모드로 보낸 뒤에야 알게 되면 안 된다. 화면용 요약은 **얕게**(하위 전수 순회·트리 크기 추정 없이) 재고, 전수 판정은 1단계가 소유한다 |
| 진단 대상을 배포 대상 목록으로만 잡기 | 웹 흐름이 **실제로 쓰는 경로 전부** — 의존성 디렉토리는 배포 대상 목록에 없지만 적용 단계가 덮어쓰고 되돌리기도 그리로 복원한다. 빠뜨리면 「진단은 통과했는데 적용에서 실패」가 그대로 재현되고, 그때는 되돌리기까지 부분 실패한다 |
| 중단된 진행을 운영자가 손으로 이어 가게 두기 | 화면이 **스스로 이어간다** — 진행·되돌리기 상태를 그리는 지점이 마운트될 때 자동으로 다음 단계를 부른다. 없으면 창을 닫은 운영자의 사이트가 점검 모드에 멈춘 채 남고, 실패 시 「조작 없이 되돌린다」도 그 호출에 기대므로 함께 무너진다. 자동 경로에는 페이지 수명당 상한을 두어 상한으로 멈춘 진행이 무한 재개되지 않게 한다 |

명령행과 웹은 **같은 서비스를 같은 순서로** 부른다. 순서를 아는 지식이 두 곳에 있으므로,
한쪽에 단계가 늘어도 다른 쪽은 따라가지 못한다 — 그 상태는 오류가 아니라 「어느 한쪽에서만
나는 결함」으로만 드러난다. `CoreUpdatePipelineParityTest` 가 명령행의 서비스 호출 집합을
소스에서 도출해 웹이 그 전부를 덮는지 보고, 웹이 일부러 부르지 않는 것은 **사유와 함께**
선언하게 한다 (그 선언이 낡으면 그것도 red 다).

> 상세: [core-update-system.md §15](../backend/core-update-system.md) · [api/core-update.md](../backend/api/core-update.md)
> 계약 테스트: `CoreUpdateStepContractTest`(순서 불변식 · 단계 이름 · 면제 목록 대칭) · `CoreUpdatePipelineParityTest`(명령행↔웹 호출 집합) · `CoreUpdateSafeDefaultsTest`(입력 표면 부재 · 명령행 옵션 존치) · `CoreUpdateRunStateTest`(재개 · 점유)

## 코드가 남기는 파일에는 정리 주체가 있다

설치·업데이트·백업 경로는 파일을 남긴다. 그중 **비밀을 담은 것**(DB 자격증명·`APP_KEY`)과 **사용자 파일의 사본**은 누적이 저장 공간 문제가 아니라 **노출** 문제다. 남기는 코드를 쓸 때 걷는 주체를 함께 쓰지 않으면 그 파일은 영구히 쌓이고, 오류도 경고도 남지 않는다.

| 금지 | 올바른 사용 |
|------|------------|
| 파일을 남기면서 걷는 주체를 두지 않음 | 생산자 곁의 스윕(진행 중 요청 보호용 나이 하한) **또는** `StorageLeftoverPruneService` 의 대상군. 둘 다 없으면 그 파일은 영구 잔존한다 |
| 임시 이름의 **생성 규칙**을 생산자와 정리자가 각각 리터럴로 가짐 | 규칙을 상수가 소유하고 양쪽이 그것을 본다 — 갈리면 정리자의 모집단이 조용히 빈다 |
| 생산자와 정리자의 **후보 디렉토리 목록**이 다름 | 같아야 한다. 한쪽만 아는 디렉토리의 잔여물은 다른 쪽 모집단 밖이다 |
| `@filemtime()` 실패를 「아주 오래됨」으로 읽어 **삭제** | 조회 실패는 **보존** — `(int) false === 0` 이라 `time() - 0` 이 언제나 하한을 넘어 나이 게이트가 통째로 무력해지고, 진행 중인 다른 요청의 파일을 지운다(fail-open) |
| 남기는 파일을 `.gitignore` 에 등재하지 않음 | 등재한다 — `git add -A` 한 번으로 자격증명·사용자 업로드가 저장소에 들어간다 |
| 백업 정렬의 마지막 결정자가 **동률을 허용** | 전순서를 만든다. `Ymd_His` 스탬프도 `filemtime()` 도 **초 해상도**라 같은 초의 둘은 양쪽 다 같아진다 — 그때 비교자가 0 을 돌리면 「최신 1개 보존」이 열거 순서에 좌우된다 |
| 새 정리 대상군을 서비스에만 추가 | 운영자 화면의 라벨 표에도 추가 — 라벨에 없는 대상군은 합계에서도 목록에서도 빠진다 |

> 생산자 상수 대조 · 라벨 대칭 · 최신 1개 보존 · 열거 순서 독립성은 정적 검사로 판정할 수 없어 계약 테스트가 소유한다

## 라우트 캐시 안전성

`route:cache` 가 걸리면 `RouteServiceProvider::boot()` 이 캐시 로드로 분기해 라우트 파일 자체가 실행되지 않는다. 클로저는 직렬화 형태로 복원되므로 문제가 아니다 (`routes/web.php` SPA catch-all 이 증거). 깨지는 것은 오토로드되지 않는 심볼 참조뿐이다.

| 금지 | 올바른 사용 |
|------|------------|
| 라우트 파일에 전역 함수 선언 + 핸들러가 호출 | 로직을 클래스(`app/Support/…`)로 옮기고 핸들러는 위임만 |
| 파일 스코프 변수를 핸들러가 `use` 없이 참조 | 클래스 상수 또는 `use ($var)` 로 클로저에 캡처 |
| 벤더/프로바이더가 `boot()` 에서 조건부 등록하는 라우트에 의존 | 그 URI 를 G7 라우트 파일이 직접 소유 |

전역 함수 위반은 `Call to undefined function` 500 인데 예외의 `file` 이 `laravel-serializable-closure://` 라 원인 파일이 스택에 드러나지 않는다. 프로바이더 등록분이 사라지는 이유는 별개다 — `Router::setCompiledRoutes()` 가 `booted` 콜백에서 라우트 컬렉션을 통째로 교체하므로 그보다 앞선 등록은 조건 충족 여부와 무관하게 폐기된다(프레임워크 자신의 `BroadcastManager::routes()` 는 `routesAreCached()` 가드를 갖지만 모든 패키지가 그렇지는 않다). 자동 검증이 라우트 파일의 전역 함수 선언을 차단한다. 상세: [routing.md](../backend/routing.md) "캐시 안전한 라우트 작성".

## 조건부로만 열리는 라우트군의 게이트 (디버그·개발 라우트)

특정 조건에서만 열려야 하는 라우트군은 판정을 핸들러 안이 아니라 그룹 미들웨어에 둔다. 게이트가 핸들러마다 흩어져 있으면 라우트를 추가할 때 함께 적는 것을 잊게 되고, 빠뜨려도 예외도 로그도 남지 않는다 — 그 엔드포인트가 정상 응답하는 것이 유일한 증상이다.

| 금지 | 올바른 사용 |
|------|------------|
| 디버그 라우트 핸들러 안에서 `DebugGate::isEnabled()` 로 개별 판정 | `bootstrap/app.php` 의 그룹 래퍼(`Route::middleware(['api', 'debug.gate'])`)가 단일 부착 |
| catch-all 제외 패턴에 예약 프리픽스 누락 (`_boost`·`modules`) | `(?!admin)(?!api)(?!plugins)(?!_boost)(?!modules)` 전수 제외 — shadow 를 보호로 삼지 않는다 |
| 게이트 부착을 행위 테스트(403 이 나오는지)로만 확인 | 라우트군 전체의 `gatherMiddleware()` 에 게이트 별칭이 있는지 단언하는 등록 계약 테스트 + 모집단 가드 |
| 그룹 게이트가 라우트 캐시에도 구워질 것이라 가정 | 캐시 상태에서의 차단도 검증 — 라우트 캐시는 확장 수명주기 지점에서 자동 생성되어 오히려 흔한 상태다 |
| `withRouting(channels: ...)` 로 채널 정의를 로드 | 게이트된 인증 라우트가 `BroadcastChannelRegistrar::ensureRegistered()` 로 `routes/channels.php` 를 로드(7.1.5) — `channels:` 인자는 `Broadcast::routes()`(게이트 없는 `/broadcasting/auth`)까지 자동 등록해 킬스위치 우회로를 만든다 |

catch-all shadow 는 보호처럼 보인다는 점이 위험하다. 가려진 라우트는 도달 불가라 게이트가 없어도 증상이 없고, 제외 패턴이 한 줄 바뀌는 순간 무방비로 노출된다 — 실제로 `_boost` GET 4종이 그 상태였고, 같은 그룹의 `DELETE clear` 는 shadow 밖이라 운영 환경·`APP_DEBUG=false` 에서 미인증 200 으로 `storage/debug-dump` 전체를 지웠다(공개#128). 등록 계약 축을 행위 테스트로 대체할 수 없는 이유도 같다: 가려진 라우트는 행위상 "막힌 것" 과 구분되지 않는다.

자동 검증이 디버그 라우트 파일의 개별 게이트를 차단하며, 부착·행위·캐시 축과 방송 인증 라우트 단일성은 테스트가 잠근다. 상세: [routing.md](../backend/routing.md) "디버그·개발 라우트는 그룹 단위로 게이트한다".

## 웹 요청 안의 커맨드 실행 (실행 모드)

웹 요청 안에서 Artisan 을 실행하는 지점(인스톨러·업데이트·예약 작업)은 실행 방식을 호출부가 고르지 않는다. `php artisan …` 스폰이 막힌 호스팅(`disable_functions`)에서는 그 경로만 터지고, 그 경로는 무CLI 환경에서만 터져 개발 환경에서는 발견되지 않는다.

| 금지 | 올바른 사용 |
|------|------------|
| 웹 도달 코드(컨트롤러·서비스·인스톨러·예약 작업)에서 `proc_open`/`exec` 로 `php artisan …` 을 직접 스폰 | `App\Execution\CommandRunner` 경유 — `CommandRunnerResolver::resolve()->run($command, $params)` (모드 결정: 명시 인자 > `system.execution_mode` > `ExecutionEnvironment::detect()`). **인스톨러는 Laravel 부팅 전이라 이 클래스를 부를 수 없다** — `installerRunArtisan($command, $parameters)` 단일 지점을 쓴다 ([execution-mode.md](../backend/execution-mode.md) §4.1) |
| `function_exists('proc_open')` 등으로 실행 함수 가용성을 직접 판정 | `ExecutionEnvironment::hasFunction()` — `function_exists` + `disable_functions` 를 함께 본다 (인스톨러도 같은 클래스를 `require_once` 로 공유) |
| 호스팅이 차단할 수 있는 함수(`exec`·`proc_open`·`putenv`·`disk_free_space`·`opcache_*`·`ini_get`·`ini_set`·`error_log` 등)를 가드 없이 **호출** | 호출 전에 `ExecutionEnvironment::hasFunction()` 으로 판정하고 대체 경로를 둔다. `@` 는 가드가 아니다 — PHP 8 은 차단 함수를 함수 테이블에서 제거하므로 그 호출은 `Error`(치명)이고 `@` 는 진단 억제일 뿐이다. 가드가 진입점에 있는 형태는 정상이며 그 자리에 면제 표식을 남긴다. 인스톨러 코드(`public/install/**`)에서는 `chmod`·`glob`·`uniqid` 도 같은 가드 대상이다 — 그 범위는 응답 봉투가 서기 **전** 에 불리는 자리라, 막히면 오류 화면조차 서지 못하고 첫 화면이 백지가 된다 |
| 확장 vendor 를 `_pending` 소스에서만 `VendorResolver` 로 구성 | 설치·업데이트 **양쪽**이 resolver 를 경유한다. `_bundled` 소스 설치(웹 인스톨러의 정상 경로)와 `--force` 재설치가 빠지면 `--vendor-mode=bundled` 가 무시되고 raw composer 만 남아, composer 를 실행할 수 없는 호스팅에서 vendor 가 빈 확장이 「설치 완료」로 남는다(DB 에는 `bundled` 로 기록되고 이후 업데이트만 그 모드를 상속한다) |
| `php artisan schema:dump` 산출물(`database/schema/*.sql`) 커밋 | 마이그레이션만 커밋 — `migrate` 가 덤프를 발견하면 `mysql` 바이너리를 스폰한다 |
| 허용값이 닫힌 설정 키(`system.execution_mode`·`general.asset_url_mode`)의 허용값 규칙을 한쪽 FormRequest 에만 부착 | `EnumeratedSettingValues` 표 하나를 벌크(`SaveSettingsRequest`)·단건(`UpdateSettingRequest`) 양쪽이 공유 — 한쪽만 검사하면 다른 쪽이 우회로가 되어 임의 문자열이 설정 파일에 남는다 |

불확실할 때의 기본값은 subprocess 다(기본값 불변) — inprocess 는 스폰 불가가 확인된 환경에서만 고른다. 정적 검사가 직접 스폰과 `schema:dump` 산출물을 차단한다. 아직 러너로 옮기지 못한 기존 스폰 지점은 그 자리에 옮기지 못한 사유를 주석으로 남기며, 그 주석이 곧 이관 대상 목록이다. 정적 검사는 `function_exists` 직접 판정도 차단하며, 아직 옮기지 못한 지점은 그 자리에 사유를 주석으로 남긴다. 정적 검사는 **무가드 호출** 축도 함께 본다 — 실행 함수 가용성 판정과는 다른 축이며, `artisan` 이 아닌 것을 무가드로 스폰하는 곳(`exec('which unzip')` 등)이 그 자리다. 대상에는 런타임 ini 접근(`ini_get`·`ini_set`)과 진단 채널(`error_log`)도 들어간다 — 셋 다 응답 봉투가 서기 전에 불려서, 막히면 첫 화면이 백지가 된다. 특히 `ini_get` 은 가드 판정의 단일 출처 자신(`ExecutionEnvironment::hasFunction()` 이 `disable_functions` 목록을 읽는 자리)에서 무가드로 불리고 있었다 — 그 한 줄이 죽으면 「가드가 있으니 안전하다」고 선언한 지점이 전부 동시에 무너진다. 짝이 있는 함수는 함께 본다(`ini_set` 만 다루고 `ini_get` 을 빼면 그 자리가 사각이다). 아직 가드를 두지 못한 지점은 그 자리에 사유를 주석으로 남긴다. 허용값 표 공유는 코드 리뷰에서 확인한다. 확장 vendor 의 설치·업데이트 대칭은 테스트가 소스 계약으로 고정한다. 상세: [execution-mode.md](../backend/execution-mode.md) · [vendor-bundle.md](../extension/vendor-bundle.md).

### 보안 게이트 대칭성 (KVE-2026-1914/1915/1919)

접근 게이트와 권한 등급 상한은 한 경로에만 있으면 다른 경로가 조용한 우회로가 된다. 게이트는 생산 지점(부모 비밀 판정 · 소유권 판정 · 등급 판정) 한 곳을 SSoT 로 두고, 같은 데이터를 내보내는 소비 경로 전부가 그 게이트를 경유해야 한다.

| 금지 | 올바른 사용 |
|------|------------|
| 비밀/비공개 부모(게시글)의 비밀 게이트를 하위 리소스(댓글·첨부·문의) 독립 엔드포인트에서 재적용하지 않음 | 부모 비밀 판정을 하위 전 경로(훅·서비스·첨부 서빙·댓글 목록)에 재적용 — PostResource 한 곳만으로는 부족하다 (KVE-2026-1914) |
| hash 기반 file-serving(preview/download)이 소유권·비밀·발행 상태 검사 없이 서빙 | preview 와 download 가 동일 게이트 공유 — 미발행·비소유·비밀 첨부는 404 (KVE-2026-1914 A-3/S-1/S-2) |
| User/Role 의 쓰기·상태변경·권한부여 경로가 삭제 경로보다 약한 등급 가드 | 전 경로에 동일 등급-상한(rank ceiling)을 대칭 적용 — 정적 라우트(bulk)는 스코프 미들웨어가 우회되므로 서비스 계층에서 강제한다 (KVE-2026-1919) |
| 저장측 레이아웃 표현식 검증(SafeLayoutExpressions)을 문자열 endpoint 필드에만 부착 | 표현식이 실릴 수 있는 배열 트리 전체(`content`)에 부착 — 문자열 한정 부착은 `is_array` 가드로 무력화되어 no-op 이 된다 (KVE-2026-1915) |
| 배열 트리 순회용 규칙(`NoExternalUrls`)이 문자열 필드에도 부착돼 `is_array` 로 조용히 통과 | 규칙이 문자열 스칼라도 처리하거나, 그 자리에서 떼어낸다 — 부착만 해두고 통과시키는 상태가 최악이다 |
| 같은 저장 대상의 FormRequest 마다 부착 규칙이 다름 (편집기 경로만 누락) | Store·Update·Content·ExtensionContent 4경로 동일 강도 — 편집기 저장 경로가 가장 약하면 그 경로가 우회로다 |
| same-origin 을 `//` 접두·scheme·`/` 시작 **문자열 검사**로만 판정 | 브라우저 URL 파서와 동일 정규화(tab·LF·CR 제거 → 백슬래시를 슬래시로 → 선행 슬래시 런 접기) 후 판정 — `/\/evil.com/x.js` 는 문자열상 path 지만 브라우저는 외부 origin 으로 해석한다. 런타임·저장측·자동 검증 3층이 같은 정규화를 공유한다 (KVE-2026-1915 B-2) |
| same-origin 판정만 정규화하고 **신뢰 호스트 추출(`hostOf`)은 원문**으로 판정 | 두 판정이 같은 `if` 안에서 이어지므로 정규화도 공유 — 어긋나면 `https://evil.com\@cdn.신뢰.com/x.js` 가 저장측에서만 신뢰 호스트로 보여 통과한다 |
| 정적 일괄 라우트(`bulk-*`)에 등급 상한만 적용하고 **스코프 축은 비움** | 라우트 모델이 없으면 미들웨어 스코프 검사가 스킵되므로 서비스가 상세 경로와 **같은 스코프 판정**(`PermissionHelper::filterByScope`)을 재적용 — 등급 축만 막으면 스코프 축이 우회로다 (KVE-2026-1919) |
| 권한 상한(ceiling) 검사를 DB 쓰기 **뒤**에 배치 | 가드 → 쓰기 순서 — 쓰기 뒤에 검사하면 거부된 요청이 고아 행·반영된 속성 변경을 남긴다. 회귀 테스트는 403 뿐 아니라 **상태 불변**까지 단언한다 |
| 같은 리소스를 쓰는 public 서비스 메서드 중 일부만 보호 가드 보유 | 형제 public 메서드 전부 동일 가드 — 서비스는 확장에 열려 있으므로 "현재 호출부가 없다" 는 방어가 아니다 |
| 라우트 파라미터가 Model 로 resolve 되지 않는 쓰기 경로를 미들웨어 스코프 검사에 맡김 | 서비스 계층에서 재적용 — 스킵 조건은 정적 경로(`bulk-*`·`reorder`)뿐 아니라 **파라미터명 불일치**(`{id}` + `int` 타입힌트)도 있고, 후자는 상세 경로까지 무가드다 |
| 순서 변경·일괄 작업의 스코프 거부를 "대상 일부 제외" 로 처리 | 순서·트리처럼 집합 전체가 하나의 값인 작업은 **전량 거부** — 일부만 반영하면 나머지와 어긋난 상태가 저장된다 |
| 가시성 판정을 호출부가 넘기는 옵트인 플래그(`$filters['is_public'] ?? false`)에 의존 | 열람자 신원 기반 fail-closed — 옵트인은 호출부가 빠뜨리면 조용히 열린다(읽기만 하고 쓰는 곳이 없는 사문 플래그가 실재했다) |
| 부모 상태로 판정하는 게이트를 `$x->parent && …` 로 작성 | 부모를 못 읽으면 차단 — 부모가 soft-delete 되면 조건이 성립하지 않아 통과한다 |
| 리소스 `abilityMap can_*` 을 연관/타 리소스 권한으로 게이팅 | 그 엔드포인트의 라우트 권한(SSoT)과 **같은 리소스 prefix** — 상승 방지는 게이트 이중화가 아니라 rank ceiling 이 담당한다 |

이 결함군은 예외도 오류도 남기지 않는다 — 약한 경로가 정상 응답을 내보내는 것이 유일한 증상이다. secret 게이트 재적용·hash 서빙 게이트·rank 대칭·URL 판정 3층 동형·정적 bulk 스코프 재적용·가드 선행·형제 메서드 가드 패리티·abilityMap prefix 정합은 의미 판정 영역이라 자동 검증이 일부만 덮으므로, 부모 변경·하위 서빙·등급 경로·URL 검증 지점을 건드릴 때 코드 리뷰에서 대칭성을 확인한다.

> 상세: [validation.md](../backend/validation.md), [service-repository.md](../backend/service-repository.md), [frontend/security.md](../frontend/security.md)

### 공개 응답의 회원 개인 연락처

응답은 화면과 무관하게 나간다. 인증 없이 열람되는 목록·상세·댓글·리뷰에 회원 이메일을 직렬화하면,
그 화면이 이메일을 그리지 않아도 응답 본문에서 회원 주소록을 통째로 수집할 수 있다.
"소비 화면이 관리자 전용" 이라는 사실은 방어가 아니다.

| 금지 | 올바른 사용 |
|------|------------|
| `'email' => $this->user->email` (게이트 없음) | `'email' => $this->canExposeMemberEmail($request, $this->user_id) ? $this->user->email : null` |
| 헤더·쿼리 등 클라이언트가 보내는 값으로 노출 판정 | 요청이 도달한 **컨트롤러**(`AdminBaseController` 여부)로 판정 — 클라이언트가 못 바꾼다 |
| "이 Resource 는 관리자 라우트 전용" 이라 게이트 생략 | 부착 비용 0(관리자 응답은 true) — 다음 사람이 공개 경로에 붙이는 순간 그 전제가 사라진다 |
| 노출을 막으려고 필드 자체를 제거 | 값만 `null` — 필드를 없애면 응답 구조가 바뀌어 소비처가 깨진다 |
| Repository·Service 가 Resource 없이 조립해 캐시에 저장하는 배열에 회원 이메일 | 값 `null` — 캐시는 호출자 권한과 무관하게 채워져 모든 요청이 같은 값을 받으므로 응답 시점 게이트가 닿지 않는다. 키를 바꾼 캐시는 키 이름도 바꿔 옛 값을 다시 읽지 않게 한다 |
| 파일 어딘가에 게이트가 있으니 그 파일의 이메일 직렬화는 전부 안전하다고 간주 | 줄마다 판정 — 같은 파일 안에 게이트된 줄과 안 된 줄이 섞여 있던 사례가 실제로 있었다 |
| 관리자 내부 메모(주문 관리자 메모·마일리지 처리 메모·처리 관리자)를 고객·회원 응답에 그대로 싣기 | `canExposeAdminNote($request)` — 이메일 게이트와 같이 도달 컨트롤러로 판정하되 **본인 예외가 없다**(자기 주문에 달린 관리자 메모도 고객에게 보이면 안 된다) |
| 공개 경로 Resource(게시글·댓글·게시판·상품평·상품문의·`Public*Resource`)에 휴대폰·주소 키 추가 | 값 `null` 또는 `canExposeMemberEmail()` 로 관리자·본인 응답에만 — 이 Resource 들은 비로그인 요청에 그대로 나가는 유일한 방어선이다 |

이메일 외의 개인 연락처(휴대폰·주소)를 새로 직렬화할 때도 같은 기준을 적용한다.

> 상세: [api-resources.md "회원 이메일은 공개 응답에 싣지 않는다"](../backend/api-resources.md)

## 서버가 조건에 따라 다른 형태의 200 을 돌려주는 엔드포인트

같은 엔드포인트가 설정·상태에 따라 **다른 형태의 2xx** 를 낸다면, 프론트는 형태를 판별한 뒤에 읽어야 한다. 한 형태만 가정하면 다른 형태에서 필드 접근이 그 자리에서 던지고, 그 원문이 오류 박스에 영문으로 노출된다. 서버는 정상 응답했으므로 **서버 로그에는 흔적이 없다** — 깨진 것은 클라이언트뿐이다.

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| 응답 타입을 한 형태로 고정 선언하고 `response.data.user.*` 를 바로 읽기 | 판별 유니온으로 세 형태를 표현 (`LoginResult` = `{status:'authenticated', user}` \| `{status:'two_factor_required', challenge}` \| `{status:'password_change_required', challenge}` — 세 번째는 engine-v1.77.0+) |
| 저장 지점에 형태 가드 없이 `setToken(response.data.token)` | 비어 있지 않은 문자열만 저장 — `localStorage` 는 무엇을 넣든 문자열로 바꾸므로 `undefined` 가 `"undefined"`(truthy)로 남아 이후 모든 요청이 `Bearer undefined` 로 나가 401 이 된다 |
| 대체 형태 분기를 사용자 경로에만 두고 관리자 경로는 그대로 | 관리자 경로가 먼저 500 이 되면 설정을 되돌릴 수단까지 사라진다 — 두 경로 동시 적용 |
| `onSuccess` 후속 액션에 조건 없이 성공 처리를 나열 | 대체 형태에서 실행되면 안 되는 액션마다 `if:"{{!response.대체형태플래그}}"` |
| `onSuccess`·시퀀스 안에서 방금 저장한 상태(`_global.*`/`_local.*`)를 형제 액션의 `if`·값으로 재독 | 그 시점 컨텍스트는 아직 갱신 전이다 — `{{response.*}}` 만 읽는다 (`onSuccess` 결과는 `handleSequence` 의 상태 동기화 대상이 아니다) |
| 서버가 제공하는 기능의 프론트 화면 부재를 "미사용" 으로 간주 | 토글을 켠 사이트에서만 드러나는 미구현이다 — 서버 토글 ↔ 화면 존재를 전수 대조 |

착수 전 전수조사 축은 **"서버가 대체 형태 2xx 를 내는 엔드포인트 ↔ 프론트 처리 여부"** 다. 그리고 **"서버 토글 ON 시 프론트 화면 존재 여부"** 를 함께 본다 — 2단계 인증은 도입 후 여러 버전 동안 입력 화면이 없었고, 그 토글을 켠 사이트에서만 전원 로그인 불가로 나타났다(공개 #133).

> 상세: [auth-system.md "2단계 인증 로그인"](../frontend/auth-system.md)
> 자동 검증으로는 잡히지 않는다 — 응답 변종은 서버 분기의 의미 판정이므로 코드 리뷰에서 확인한다.

## 제3자 라이브러리는 쓰기 경로를 지정받는다

제3자 라이브러리는 캐시·임시파일 경로를 설정하지 않으면 **자기 설치 폴더**(vendor 안)나 시스템 temp 에 쓴다. 표준 Laravel 배포는 웹서버에 `storage/` 와 `bootstrap/cache` 만 쓰기 권한을 주므로 그 쓰기는 실패하는데, 실패가 예외가 아니라 PHP 경고라 Laravel `HandleExceptions` 가 `ErrorException` 으로 승격시켜 요청이 500 이 된다. 해시당 1회만 기록하는 라이브러리라면 캐시가 영영 생기지 않아 **매 요청이 같은 실패를 반복**한다 — 개발 머신에서는 vendor 가 쓰기 가능해 한 번 성공하고 끝나므로 재현되지 않는다 (공개 #125).

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| 제3자 라이브러리를 기본 설정 그대로 인스턴스화 | 캐시·임시파일 경로를 `ExtensionStoragePath::module($id, 'cache/…')` 로 명시 — 기본값은 **라이브러리 자기 설치 폴더**다 |
| 쓰기 경로만 지정하고 디렉토리 생성은 라이브러리에 맡김 | `FilePermissionHelper::ensureWritableDirectory()` 로 **먼저 확보한다** — 라이브러리는 대개 하위 디렉토리만 만들고, base 가 없으면 경고만 내고 끝난다 |
| 확보 절차(억제 생성·chmod·setgid·소유권·쓰기 판정)를 호출부가 자기 안에 복사 | 코어 프리미티브 한 곳에서 수행 — 사본은 서로 다른 하드닝을 갖고 갈라진다(실제로 억제 mkdir·setgid·`clearstatcache` 가 사본마다 한쪽씩 빠져 있었다) |
| 확장 저장 경로를 `storage_path('app/modules/…')` 로 직접 조립 | `ExtensionStoragePath::{module,plugin}()` — 디스크 root 가 단일 출처이고 테스트 환경을 인지하므로, 확장이 `runningUnitTests()` 분기를 복사하지 않는다. 복사본은 한 곳만 빠뜨려도 그 확장의 테스트가 **운영 설정 파일을 덮어쓴다** |
| 캐시 쓰기 실패를 그대로 500 으로 흘림 | 캐시는 성능 장치다 — 확보 실패 시 캐시만 끄고 본래 기능은 계속한다. **정화·검증 자체를 건너뛰는 폴백은 금지** |
| 폴백 통지를 `Log::warning` 으로 남김 | `Log::error` — 출하 기본 로그 수준(`config/settings/defaults.json` 의 `log_level`)이 `error` 라 `warning` 은 기본 설치 상태에서 파일에 기록되지 않는다. 기능은 성공하므로 그 통지가 유일한 흔적이다 |

확보 프리미티브는 **예외도 PHP 경고도 내지 않는다** — `File::ensureDirectoryExists()` 는 `mkdir()` 을 억제 없이 부르므로 생성 실패가 `E_WARNING` → `ErrorException` 으로 승격되어, 막으려던 500 이 다른 줄에서 그대로 난다. 실패는 `bool` 과 사유(`occupied_by_file` / `ancestor_not_writable` / `create_failed` / `not_writable`)로 올라오고, 그 사유를 통지에 실어 운영자가 고칠 대상을 지목한다.

경로는 `ExtensionStoragePath` 가 해석한다. `getBasePath('cache')` 는 `Storage::disk()->path()` 위임이라 비로컬 디스크(S3 등)에서 파일시스템 경로가 아니게 되는데, 그러면 라이브러리가 상대경로를 CWD 기준으로 해석해 **조용히 엉뚱한 곳에 쓴다** — 지금 결함보다 나쁘다. 대부분의 정의 캐시는 `file_put_contents` 로 쓰는 로컬 전용 장치다.

> 상세: [storage-driver.md](../extension/storage-driver.md) "제3자 라이브러리에 절대 경로를 넘길 때", [service-repository.md](../backend/service-repository.md) "서비스가 제3자 라이브러리를 붙일 때"

그래서 확장 저장 경로를 `storage_path()` 로 **직접 조립하지 않는다** — 디스크 root 는 운영자가 옮길 수 있고, 손으로 이은 경로는 그 이동을 따라가지 못한 채 빈 트리를 가리킨다(오류 없이 자산만 사라진다). 해석은 `ExtensionStoragePath` 단일 출처가 소유하며 정적 검사가 직접 조립을 차단한다.

## 공개 자산 직접 URL 은 운영자 선언으로만 열린다

저장된 파일의 주소를 직접 URL(CDN)로 내보내면 서버 스트리밍 경로가 통째로 건너뛰어진다. 그 경로에 게이트가 있으면 게이트가 사라지고, 대상 저장소가 실제로는 비공개면 발급된 주소가 403 이 된다. 둘 다 예외도 로그도 남기지 않는다 — 그 이미지들만 조용히 깨지거나, 막아야 할 파일이 조용히 열린다.

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| `filesystems.disks.{disk}.url` 이 설정돼 있다는 이유로 그 디스크를 공개로 간주해 직접 URL 발급 | 운영자가 명시 선언한 `core.storage.public_asset_disk` 와 **행 disk 가 일치할 때만** 직접 URL. `url` 설정 유무는 "URL 을 만들 수 있는가" 이지 "익명 읽기가 되는가" 가 아니다 |
| 권한·게이트(비밀글·소유권·발행 상태·본인인증·다운로드 카운트)가 걸린 첨부 경로를 직접 URL 로 전환 | 게이트가 없는 완전 공개 자산 카테고리에만 배선. 게이트가 있는 경로의 응답 `url` 칸은 그 게이트를 통과하는 서빙 URL 로 채운다 |
| 공개 판정을 `PublicAssetDisk::resolve()` 밖에서 사본으로 재작성 | 판정은 그 단일 지점 경유. `''`·`'none'`·config 에 없는 고아 디스크가 등가 비교만으로 통과하는 것을 막는다 |
| 행 disk 로 `withDisk()` 를 무검증 호출 | 존재 확인 후 폴백 — 공개 자산 디스크가 플러그인 등록 디스크일 수 있고, 그 플러그인 비활성화 시 무인증 공개 서빙 라우트가 **500** 이 된다 |
| 직접 URL 로 전환하면서 "행 삭제 = 접근 차단" 전제를 그대로 둠 | 직접 URL 은 행과 무관하게 파일을 가리킨다 — 회수 수단(파일 삭제)과 그 한계를 문서에 남긴다 |
| 서버가 스스로 발급하는 자산 주소(프록시 서빙 URL)를 절대 URL 로 만듦 | 사이트 상대 경로 — 절대면 저장 규칙(외부 URL 차단)이 자기 주소를 외부로 차단해 image 위젯의 업로드 → 저장이 422 가 되고(배경은 `style` 이라 스캔되지 않아 로고에서만 드러났다), 저장된 레이아웃이 발급 시점 도메인·스킴에 묶인다 |
| 저장 규칙의 "외부" 판정을 스킴 접두 문자열로만 두고 자기 주소를 예외 없이 차단 | 사이트 자기 host(`app.url`)·선언된 공개 자산 디스크 host 는 외부가 아니다 — `SiteAssetHosts` 단일 판정(정규화 후 host 등가 비교). 접두 비교는 `host.evil.com`·`host@evil.com` 을 통과시키고, 요청 `Host` 헤더는 위조 가능해 근거가 아니다 |

이 결함군의 유일한 증상은 화면이다: 직접 URL 이 403 을 돌려주면 그 이미지들만 깨지고, 게이트가 우회되면 정상 200 이 나간다. 서버 로그에는 어느 쪽도 흔적이 없다.

**확장 선례 — 행 disk 기준 (설정을 꺼도 직접 URL 유지)**: 코어 레이아웃 첨부는 위 표대로 「행 disk = 지금 설정된 공개 자산 디스크」일 때만 직접 URL 을 낸다. 번들 확장의 완전 공개 이미지(이커머스 상품·카테고리·리뷰, 에디터 이미지, 히어로섹션 배너 이미지·영상, 팝업 이미지)는 **행 disk 드라이버의 `url()` 이 주소를 주면** 직접 URL 을 낸다 — 운영자가 공개 자산 디스크를 켠 뒤 그 디스크에 올린 행은 설정을 다시 꺼도 계속 직접 주소로 나간다(제품 결정 #878). 이 갈래가 허용되는 근거는 두 가지다: 그 행은 운영자가 공개 디스크로 **선언했던 시점에** 올라갔고, 대상 카테고리는 공개 화면에 그대로 노출되는 자산이다. 예외로 이커머스 리뷰 이미지는 서빙 경로에 노출·서명 게이트가 있지만 공개 자산으로 배선돼 있어, 리뷰를 숨겨도 이미 발급된 직접 URL 은 회수되지 않는다(스토리지 드라이버 문서 「알려진 한계」). 한계: 설정을 꺼도 그 디스크의 파일은 계속 열리며, 닫으려면 그 행(파일)을 지워야 한다. 고아 disk(설정에서 사라짐)·빈 disk 는 직접 URL 없이 서빙 경로로 폴백한다(`RowDiskStorage::resolve()`).

직접 URL 을 내더라도 **썸네일 축은 서빙 경로**로 남긴다: 응답은 원본 한 장의 주소(`direct_url`·`download_url`)와 썸네일 기준 주소(`url`·`preview_url` — 같은 출처 API 경로, 서버가 `?size=` 파생본을 공개 썸네일 디스크로 302. 게이트가 있는 리뷰 이미지는 비공개 썸네일을 스트리밍)를 함께 싣는다. 코어 썸네일 판정(`ThumbnailUrl::isThumbnailableUrl()`)은 같은 출처 + 등록 경로만 대상이라, 직접 URL 하나만 내리면 화면의 썸네일·srcset 이 조용히 사라지고 원본만 받는다.

> 상세: [storage-driver.md](../extension/storage-driver.md) "공개 자산 전용 디스크 분리"
> 이 규칙은 자동 검증으로 판정할 수 없다 — "이 경로에 게이트가 있는가"·"행 disk 와 설정이 같은 축인가" 는 의미 판정이므로, 회귀 테스트(특히 비공개 S3 행 + 공개 URL 설정 조합에서 서빙 라우트가 나오는 케이스)가 잠근다

## 직접 전송로는 자격증명을 스스로 싣는다

레이아웃의 `globalHeaders` 는 **데이터소스(DataSourceManager)와 `apiCall` 핸들러(ActionDispatcher)** 에만 적용된다. 코어 ApiClient(`G7Core.api.*`)를 직접 부르거나 `fetch` 를 쓰는 경로는 그 배선을 타지 않아 `Authorization` 과 `Accept-Language` 만 실린다. 게이트된 엔드포인트를 그렇게 부르면 서버는 정당한 사용자를 거부하는데, 화면은 버튼·썸네일을 이미 내준 뒤라 **예외도 콘솔 오류도 없이 그 자리만 비는 것**이 유일한 증상이다.

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| 게이트된 엔드포인트를 `G7Core.api.*` / `fetch` 로 부르며 자격증명 헤더를 생략 | 호출부가 직접 싣는다 — 비밀글 첨부는 `X-Board-Secret-View-Token`, 비회원 주문은 `X-Guest-Order-Token` |
| 자격증명이 없을 때 조용히 `return null` 로 이탈 | 회원/비회원 두 경로를 모두 구성한다 — 한쪽을 비우면 서버가 지원하는 기능이 도달 불가로만 남는다 |
| 헤더 구성을 호출부마다 복제 | 확장·템플릿 안에 단일 지점(`secretContentHeaders()` / `buildOrderRequestHeaders()`)을 두고 경유 |
| `<img src>` 에 헤더를 실으려 시도 | 이미지 태그는 헤더를 실을 수 없다 — 한시 서명 URL 을 발급하거나 blob 으로 받아 그린다 |
| 자격증명을 GET 쿼리 문자열로 전달 | 헤더로 보낸다 — 쿼리는 웹서버 접근 기록과 `Referer` 에 그대로 남는다 |

같은 기능을 여러 확장이 제공할 때는 **형제 구현의 강도가 갈리지 않는지** 확인한다. 서버가 비회원을 지원하는데 프론트 한쪽만 토큰을 보내면, 나머지 확장에서는 그 서버 기능이 존재하지만 도달 불가인 상태로 남는다.

## 프록시 뒤 요청은 스킴·IP 를 스스로 증명하지 않는다

TLS 가 앞단에서 종단되고 앱에는 HTTP 로 전달되는 구성(AWS ALB, CloudFront, Cloudflare, nginx/Apache 리버스 프록시, ngrok)에서 신뢰할 프록시가 지정되지 않으면 Laravel 은 `X-Forwarded-*` 를 전부 무시한다. 요청 객체가 평문 HTTP 로 인식되어 `asset()`/`url()` 이 `http://` 를 만들고(HTTPS 페이지에서 혼합 콘텐츠로 차단 → **사이트 전체 백지**), `$request->ip()` 가 프록시 IP 가 되어 통보 IP 화이트리스트·rate limit·IP 기록·GeoIP 가 동시에 무너진다.

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| `bootstrap/app.php` 에서 `trustProxies(at: env('TRUSTED_PROXIES'))` | `config/trustedproxy.php` 의 `'proxies' => env('TRUSTED_PROXIES')` — `withMiddleware` 클로저는 `.env` 로드 전에 평가되어 `env()` 가 항상 `null` 이다(오류 없이 no-op) |
| 신뢰 프록시를 `'*'` 로 하드코딩 | env opt-in — 앱이 직접 노출된 환경에서 `X-Forwarded-For` 위조로 기록 IP·IP 제한이 조작된다 |
| `$middleware->trustHosts()` 호출 | 호출 자체가 모든 설치처에서 Host 검증을 켠다(미등록 호스트 400) — opt-in 원칙 위반 |
| IP 화이트리스트·rate limit·IP 기록을 `$request->ip()` 로 두면서 프록시 구성을 문서화하지 않음 | 그 기능이 프록시 신뢰 설정에 의존한다는 사실을 문서에 남긴다 |
| 절대 URL 이 필요한 곳에서 요청 스킴 의존(`url()`/`asset()`)과 설정 앵커(`config('app.url')`)를 혼용 | 외부 시스템에 등록·전송되는 URL(PG 콜백·webhook 안내)은 설정 앵커, 화면 자산은 요청 기준 |
| 진단 판정을 "HTTPS 인식 실패" 로 세움 | `X-Forwarded-* 수신 중 AND 신뢰 프록시 미설정` — HTTP 전용 사이트가 프록시 뒤에 있으면 **화면은 완전히 정상 렌더되면서** webhook 403·IP 왜곡만 계속된다. HTTPS 기준 판정은 그 구성에서 침묵한다 |
| 같은 판정을 노출면(대시보드·환경설정·설치 마법사·커맨드)마다 다시 작성 | `App\Support\TrustedProxyDiagnostic` 단일 판정 — 면마다 조건을 복제하면 한 곳만 어긋나도 서로 다른 답을 내놓는다 |
| 신뢰 프록시 값을 관리자 화면에서 편집 가능하게 제공 | 읽기 전용 진단만. ① 프록시 뒤에서는 그 화면 자체가 뜨지 않는 것이 이 결함이라 정작 필요한 순간에 도달 불가(잠금 역설) ② 웹 편집이 가능해지면 관리자 계정 탈취가 곧 XFF 위조 경로가 된다 |

이 결함군은 서버 로그에 흔적을 남기지 않는다. 브라우저 콘솔의 차단 로그와 "모든 방문자가 같은 IP" 라는 데이터 상태만이 증상이며, 설치 마법사는 `X-Forwarded-Proto` 를 읽어 "HTTPS 정상" 이라고 보고하므로 운영자에게는 원인 추적 단서가 없다.

`**` 는 Laravel 내장 미들웨어에서 `*` 과 같은 코드 경로를 타므로 "모든 프록시 신뢰" 가 아니다. 프록시가 여러 단인 구성에서는 체인의 모든 프록시 IP·CIDR 를 나열해야 최초 클라이언트 IP 가 해석된다.

> 상세: [reverse-proxy.md](../backend/reverse-proxy.md)
> `config/trustedproxy.php` 의 키 계약, 신뢰/미신뢰 분기, 쿠키 Secure 자동 판정, `bootstrap/app.php` 로의 `env()` 함정 재유입 차단은 테스트가 잠근다. `url()`/`asset()`/`$request->ip()` 는 정상 사용례가 다수라 정적 금지 규칙을 두지 않는다.

## 화면이 읽는 데이터소스의 권한 폭

한 화면이 여러 엔드포인트를 읽는다. 그중 하나라도 게이트가 **그 화면의 라우트 권한보다 좁으면**, 그 데이터소스만 403 이 되어 값이 빈 채로 화면이 열린다. 그 권한 조합을 가진 운영자에게만 나타나므로 전권 계정으로는 재현되지 않고, 오류도 경고도 로그도 남지 않는다.

| ❌ 금지 | ✅ 올바른 사용 |
|--------|---------------|
| 화면 라우트 권한보다 좁은 게이트의 데이터소스에서 **동작 초기값**을 읽음 | 이미 열려 있는 응답(그 화면의 목록·상세 응답)에 그 값을 실어 나른다 |
| 그 축을 화면 권한 확대로 해소 | 값의 통로만 옮긴다 — 설정 열람 권한을 담당자에게 주는 것은 다른 결정이다 |
| 값이 비었을 때 화면이 계약 기본값으로 분기 | 서버가 **항상 키를 채워** 보낸다 — 화면 분기는 계약 기본값의 두 번째 출처가 된다 |
| 표시만 비는 경우와 동작 초기값이 비는 경우를 같이 취급 | 동작 초기값이면 처리 **결과**가 갈린다 — 우선순위가 다르다 |
| 전권 계정으로만 화면을 확인 | 그 화면 라우트 권한 **만** 가진 토큰으로 데이터소스 전건 200 을 확인 |

무너지는 방향이 "운영자가 꺼 둔 것을 켜진 것으로" 이면, 재고 복구·환불 접수처럼 되돌리기 어려운 처리가 의도 없이 실행된다. 그 값이 표시가 아니라 초기 선택값이면 화면은 정상으로 보이고 실행 결과만 갈린다.
