# 7.0.x → 7.1.0 업그레이드 안내

7.0.x 에서 7.1.0 으로 올리는 사이트 운영자를 위한 안내입니다. 코어와 함께 번들 확장(모듈·플러그인·템플릿·언어팩)을 **한 번에** 올려야 하는 이유, 업데이트 전에 확인할 것, 일괄 업데이트를 건너뛰었거나 일부가 실패했을 때의 조치, 업데이트 뒤 역할에 부여할 권한을 다룹니다.

## TL;DR (5초 요약)

```text
- 백업 → APP_URL·역할 점검 → php artisan core:update → 마지막 질문 「번들 확장 일괄 업데이트」 반드시 승인
- 7.1.0 은 요청 Host 가 APP_URL 도메인(하위 도메인·www 유무 쌍 포함)이 아니면 404, www 유무가 다른 주소는 사이트 주소로 301 — 다른 도메인은 TRUSTED_HOSTS
- 7.1.0 부터 꺼 둔 역할은 권한을 주지 않는다 — 직접 만든 역할·매니저에 환불 실행 등 새 권한은 「권한 관리」에서 직접 부여
- 건너뛰었거나 실패했으면: 원인 해결 → 모듈 → 플러그인 → 템플릿 → 언어팩(--force) 순서로 개별 업데이트 → php artisan hooks:cache
- 이커머스가 실패하면 결제 플러그인 4종은 업데이트가 중단되고, 기본 사용자 템플릿은 경고만 남기고 올라가 사용자 화면이 503 — 이커머스부터
- 업그레이드 스텝이 중단됐으면(proc_open 제한 호스팅) 출력된 core:execute-upgrade-steps 실행 → 언어팩을 language-pack:update <id> --force 로 다시 적용
- 확장이 「업데이트 중」으로 남았으면 상태를 되돌린 뒤 그 확장만 --force 로 다시 업데이트, 명령줄 PHP memory_limit 상향
- 수정 보존(keep)을 골랐으면 업데이트 결과의 「겹쳐서 운영자 것 유지」 화면을 확인해 새 기능 연결을 다시 적용
- 이미 올린 사이트에서 내 정보·방문자 통계·회원 알림함이 403 이면: php artisan core:execute-upgrade-steps --from=7.1.0 --to=7.1.0 --force --skip-migrations --skip-bundled-updates
```

## 순서

1. 업데이트 전에 데이터베이스와 사이트 파일을 백업하고, `.env` 의 `APP_URL` 이 실제 사이트 주소인지, 꺼 둔 역할과 직접 만든 역할이 있는지 확인합니다([업데이트 전에 확인할 것](#업데이트-전에-확인할-것)).
2. `php artisan core:update` 를 실행합니다.
3. 코어 업데이트가 끝나면 묻는 **번들 확장 일괄 업데이트를 반드시 승인**합니다. 레이아웃 전략은 화면을 고친 적이 있으면 「사용자가 수정한 레이아웃은 보존」을 고릅니다([수정 보존 전략을 골랐을 때](#수정-보존-전략을-골랐을-때)).
4. 일괄 업데이트 결과에 「실패」가 있거나 일괄 업데이트를 건너뛰었다면 [건너뛰었거나 실패했을 때](#일괄-업데이트를-건너뛰었거나-일부가-실패했을-때)의 순서대로 조치합니다. 업그레이드 스텝이 중단됐다는 안내가 나왔다면 [업그레이드 스텝이 중단됐을 때](#업그레이드-스텝이-중단됐을-때-proc_open-제한-호스팅)를 먼저 봅니다.
5. [업데이트 뒤 역할 관리에서 부여할 권한](#업데이트-뒤-역할-관리에서-부여할-권한)을 확인해 운영자 역할에 필요한 권한을 부여합니다.

## 업데이트 전에 확인할 것

### 사이트 주소(APP_URL)와 신뢰 호스트

7.1.0 부터 요청의 Host 가 사이트 주소(`APP_URL`)의 도메인이 아니면 요청을 받지 않습니다(404). 다음 주소는 따로 설정하지 않아도 허용됩니다.

- 사이트 주소의 도메인과 그 하위 도메인
- `www` 유무만 다른 짝 주소 — `APP_URL` 이 `https://www.example.com` 이면 `example.com` 도, `https://example.com` 이면 `www.example.com` 도 자동으로 허용합니다(IP 주소·`localhost` 에는 짝이 없습니다).

허용된 주소라도 사이트 주소가 아닌 주소(`www` 유무가 다른 주소·하위 도메인·다른 포트·별칭)로 들어온 화면 요청은 같은 경로의 사이트 주소로 이동합니다(301). API·결제·본인인증 콜백·사이트맵·정적 파일은 이동하지 않습니다. 이 동작은 **업데이트 직후 바로 켜집니다.**

- `.env` 의 `APP_URL` 이 방문자가 실제로 쓰는 주소(`https://` 포함)인지 확인합니다. 설치 때 값이 `http://localhost` 등으로 남아 있으면 업데이트 직후 사이트가 404 로 응답합니다.
- `www` 짝이 아닌 다른 도메인·별칭으로도 서비스한다면 `TRUSTED_HOSTS=example.org,shop.example.net` 처럼 콤마로 나열합니다(정확히 일치하는 주소만 허용). `APP_URL` 이 `www.example.com` 일 때 `m.example.com` 처럼 맨도메인 쪽 하위 도메인도 사이트 주소의 하위 도메인이 아니므로 이 목록에 넣어야 합니다.
- 업데이트 뒤 접속이 막혔다면 비상 조치로 `TRUSTED_HOSTS_ENABLED=false` 를 넣어 검사를 끄고, `APP_URL`·`TRUSTED_HOSTS` 를 바로잡은 뒤 다시 켭니다. 주소 이동만 끄려면 `CANONICAL_HOST_REDIRECT=false` 입니다.
- 리버스 프록시·CDN 뒤에서 운영한다면 `TRUSTED_PROXIES` 도 지정합니다(지정하지 않으면 모든 방문자가 한 IP 로 집계됩니다).

`.env` 를 고친 뒤 설정 캐시를 쓰는 사이트는 `php artisan config:clear` 로 반영합니다.

### 꺼 둔 역할과 직접 만든 역할

7.0.x 에서는 관리자 「권한 관리」에서 역할을 꺼도(사용 안 함) 그 역할의 권한이 그대로 적용됐습니다. **7.1.0 부터는 꺼진 역할은 권한을 주지 않습니다.** 업데이트 전에 「권한 관리」(`/admin/roles`)에서 꺼 둔 역할을 확인합니다.

- 코어 기본 역할(관리자·매니저·일반 사용자·비회원)과 확장이 선언한 역할(이커머스 관리자 등)은 업데이트 때 다시 켜집니다. 7.0.x 에서 꺼 두었더라도 그 역할 회원의 권한은 업데이트 전과 같습니다. 이 역할을 실제로 막으려면 업데이트 뒤 다시 끕니다 — 7.1.0 에서 끈 상태는 다음 업데이트에도 유지됩니다(관리자 역할은 끌 수 없습니다).
- **운영자가 직접 만든 역할**은 켜고 끈 상태를 그대로 둡니다. 7.0.x 에서 꺼 둔 채 회원에게 붙여 쓰던 역할은 업데이트 직후 그 회원들의 권한이 사라지므로, 계속 쓰려면 업데이트 뒤 켭니다.
- 직접 만든 역할에는 7.1.0 번들 확장의 새 권한이 자동으로 붙지 않습니다. 업데이트 뒤 [부여할 권한](#업데이트-뒤-역할-관리에서-부여할-권한)을 확인합니다.

### PHP 실행 환경 점검

코어 업데이트는 업그레이드 스텝과 번들 확장 일괄 업데이트를 별도 PHP 프로세스로 실행합니다.

- 호스팅이 `proc_open` 을 막아 두었으면(`disable_functions`) 업그레이드 스텝이 실행되지 못하고 중단됩니다. 업데이트는 그대로 진행해도 되지만, 끝난 뒤 [업그레이드 스텝이 중단됐을 때](#업그레이드-스텝이-중단됐을-때-proc_open-제한-호스팅)의 절차가 필요합니다.
- 일괄 업데이트 중 프로세스가 메모리 부족으로 끝나면 확장이 「업데이트 중」 상태로 남을 수 있습니다([확장이 업데이트 중 상태로 남았을 때](#확장이-업데이트-중-상태로-남았을-때)). 명령줄 PHP(php.ini)의 `memory_limit` 를 업데이트 동안 512M 이상으로 올려 둡니다. 별도 프로세스는 php.ini 를 다시 읽으므로 `php -d memory_limit=…` 로 실행한 명령에만 준 값은 그 프로세스에 적용되지 않습니다.

### 업데이트 시간

7.0.x 의 코어 업데이트 프로그램은 코어 파일을 바꾸고 **유지보수 모드를 해제한 뒤에** 번들 확장 일괄 업데이트를 묻습니다. 그 사이에는 새 코어와 옛 확장·템플릿이 함께 돌아가므로, 방문이 적은 시간에 진행하고 질문에 바로 답하세요.

## 일괄 업데이트를 승인해야 하는 이유

7.1.0 코어와 7.0.x 판 확장·템플릿은 함께 동작하지 않는 곳이 있습니다. 일괄 업데이트를 건너뛰면 아래 증상이 남습니다.

| 함께 올려야 하는 조합 | 건너뛰면 |
| --- | --- |
| 코어 ↔ 관리자·사용자 템플릿 | 7.0.x 관리자 템플릿이 7.1.0 에서 없어진 주소를 불러 일부 관리자 화면(환경설정 등)이 열리지 않고, 새 관리자 메뉴의 화면이 없습니다. |
| 코어 ↔ 일본어 등 언어팩 | 언어팩이 옛 판으로 남아 새 문구가 기본 언어로 나옵니다. |
| 이커머스 ↔ 결제 플러그인 4종(KG이니시스·NHN KCP·나이스페이먼츠·토스페이먼츠) | 결제 플러그인 새 판은 이커머스 1.3.0 이상이 필요합니다. 이커머스가 옛 판이면 결제 플러그인 업데이트는 중단되고(옛 판으로 유지), 억지로 맞추지 않은 조합에서는 결제 화면이 오류를 냅니다. |
| 이커머스·게시판·페이지 ↔ 기본 사용자 템플릿 | 기본 사용자 템플릿 새 판은 이커머스 1.3.0·게시판 1.2.0·페이지 1.2.0 이상이 필요합니다. 템플릿 업데이트는 의존 확장이 모자라도 경고만 남기고 적용되며, 그 뒤 사용자 화면은 의존 확장을 올릴 때까지 503 오류 화면이 됩니다. |
| 이커머스 ↔ 기본 관리자 템플릿 | 이커머스 1.3.0 의 환경설정 결제수단 목록·카드는 관리자 템플릿 1.1.0 에 새로 생긴 브랜드 마크로 간편결제 배지·로고를 그립니다. 관리자 템플릿이 옛 판(1.0.x)이면 오류 없이 배지·로고만 보이지 않습니다. |
| CKEditor5 ↔ 코어·템플릿 | 옛 CKEditor5 와 새 템플릿을 함께 쓰면 알림 메일 템플릿 편집 창에서 본문이 저장되지 않습니다. |
| GDPR ↔ 본인인증·결제 플러그인(KG이니시스·NHN KCP) | 동의·본인인증 연동 항목이 맞지 않습니다. 함께 올립니다. |
| 비즈뿌리오 메시지 ↔ 이커머스 | 주문 알림 연동이 맞지 않습니다. 함께 올립니다. |
| 게시판 ↔ 기본 사용자 템플릿 | 새 템플릿의 마이페이지 스크랩·반응·신고 화면은 게시판 1.2.0 이 필요합니다. |
| 사용 중인 템플릿 ↔ 결제 플러그인 화면 조각 | 주문 상세의 가상계좌 입금 안내·영수증·에스크로 표시는 템플릿 새 판의 자리에 붙습니다. 템플릿까지 올려야 나옵니다. |

한국수출입은행 환율 플러그인은 7.1.0 에 새로 들어온 플러그인이라 7.0.x 사이트의 일괄 업데이트 대상이 아닙니다. 새로 설치할 때 이커머스 1.3.0 이상이 필요합니다.

일괄 업데이트는 모듈 → 플러그인 → 템플릿 → 언어팩 순서로 진행합니다. 7.1.0 의 확장 업데이트는 새 판이 요구하는 의존 확장이 없거나 꺼져 있거나 버전이 모자라면 완료 안내에 경고를 붙입니다.

## 수정 보존 전략을 골랐을 때

「사용자가 수정한 레이아웃은 보존」(`--layout-strategy=keep`)은 운영자가 고친 화면을 통째로 두지 않고, 원본·운영자 판·새 판을 비교해 고치지 않은 부분만 새 판으로 바꿉니다. 비교 단위는 화면 조각(partial) 파일과 **레이아웃 최상위 키**(`computed`·`components`·`data_sources` 항목 등)입니다. 그래서 운영자가 레이아웃의 루트 `computed` 나 루트 `components` 를 고쳤다면, 새 판이 같은 키에 넣은 변경은 반영되지 않고 운영자 판이 남습니다. 이때 새 기능이 화면과 연결되지 않아 버튼이 잠긴 채 남을 수 있습니다(예: 게시판 환경설정의 일괄 적용·유형 관리·SEO 캐시 초기화 버튼).

1. 일괄 업데이트·개별 업데이트 출력의 「레이아웃 처리 결과 (수정 유지)」 표에서 결과가 「겹쳐서 운영자 것 유지」·「비교 기준 없음 — 통째 유지」·「병합 결과 검증 실패 — 통째 유지」인 화면을 적어 둡니다. 겹친 새 판 변경은 이 업데이트에서 **한 번만** 알립니다.
2. 관리자 「템플릿 관리」에서 해당 템플릿의 레이아웃 편집 화면(`/admin/templates/{템플릿 식별자}/edit`)을 열어 그 화면을 확인합니다. 버전 이력에 업데이트 직전 판과 병합 판이 남아 있어 무엇을 고쳤는지 비교할 수 있습니다.
3. 고친 부분이 더 필요 없으면 그 확장의 레이아웃을 새 판으로 다시 적용합니다. 관리자 「모듈 관리」·「플러그인 관리」의 「레이아웃 갱신」, 또는 아래 명령입니다. 이 방법은 **그 확장의 모든 화면**을 새 판으로 바꾸므로 다른 화면에서 고친 내용도 사라집니다 — 먼저 2단계에서 다른 화면의 수정 내용을 확인해 둡니다.

   ```bash
   php artisan module:update sirsoft-board --source=bundled --force --layout-strategy=overwrite
   ```

4. 고친 부분을 살려야 하면 새 판으로 다시 적용한 뒤 레이아웃 편집 화면에서 필요한 수정만 다시 넣습니다.

## 일괄 업데이트를 건너뛰었거나 일부가 실패했을 때

아래를 순서대로 실행합니다. 각 명령은 사이트 루트에서 실행하며, 번들에 들어 있는 판으로 올리도록 `--source=bundled` 를 붙입니다. 화면을 고친 적이 있으면 `--layout-strategy=keep` 을 붙여 고친 부분을 보존합니다.

모듈·플러그인·템플릿 업데이트 명령은 진행 전에 확인을 묻습니다. 스크립트나 `--no-interaction` 처럼 질문에 답할 수 없는 방식으로 돌리면 기본값(아니오)으로 취소되고 오류 없이 끝나므로, 그때는 `--force` 를 붙입니다. `--force` 는 확인을 건너뛰는 것과 함께 버전 비교 없이 같은 판도 다시 적용하므로 위 순서대로 필요한 확장에만 씁니다.

1. **실패 원인부터 해결합니다.** 일괄 업데이트 출력의 「실패:」 줄과 `storage/logs` 의 로그를 확인합니다. 이커머스가 실패하면 결제 플러그인 4종은 이커머스 1.3.0 이 필요하다는 이유로 업데이트가 중단되고(옛 판으로 유지), 기본 사용자 템플릿은 경고만 남기고 새 판으로 올라가 사용자 화면이 503 오류 화면이 됩니다. 이커머스 원인을 먼저 해결하고 이커머스 → 결제 플러그인 순서로 올리면 사용자 화면도 돌아옵니다.
2. **모듈** — 게시판·페이지·이커머스 등 옛 판으로 남은 모듈:

   ```bash
   php artisan module:update sirsoft-ecommerce --source=bundled --layout-strategy=keep
   ```

3. **플러그인** — 모듈 다음에 올립니다(결제 플러그인은 이커머스 다음):

   ```bash
   php artisan plugin:update sirsoft-pay_kginicis --source=bundled --layout-strategy=keep
   ```

4. **템플릿** — 모듈·플러그인 다음에 올립니다. 사용 중인 템플릿을 올리면 켜져 있는 모듈·플러그인의 화면 조각이 다시 등록됩니다:

   ```bash
   php artisan template:update sirsoft-admin_basic --source=bundled --layout-strategy=keep
   php artisan template:update sirsoft-basic --source=bundled --layout-strategy=keep
   ```

5. **언어팩** — 일본어 등 언어팩을 쓰는 사이트는 각 팩을 다시 적용합니다:

   ```bash
   php artisan language-pack:update g7-core-ja --force
   ```

   번들 언어팩 식별자는 `g7-{core|module|plugin|template}-{대상}-{언어}` 형식입니다(예: `g7-module-sirsoft-board-ja`, `g7-template-sirsoft-basic-ja`). 관리자 「언어팩 관리」에서 업데이트 표시가 있는 팩을 모두 올립니다.

   개별 업데이트가 실패하면 그 확장은 이전 판으로 돌아가고(명령 끝의 안내가 실제 결과를 알려 줍니다), 확장 캐시도 이전 판 기준으로 다시 만들어집니다. 그래도 실패 직후 사이트가 오류(500)를 내면 `php artisan extension:update-autoload` 를 한 번 실행하세요.

6. **훅 캐시 다시 만들기** — 마지막에 한 번 실행합니다:

   ```bash
   php artisan hooks:cache
   ```

   7.0.x 에서 만든 훅 캐시는 7.1.0 이 자동으로 쓰지 않고(리스너를 직접 찾아 등록) 이 명령으로 새로 만듭니다. 실행하지 않아도 동작은 맞지만, 요청마다 리스너를 찾는 비용이 듭니다.

## 업그레이드 스텝이 중단됐을 때 (proc_open 제한 호스팅)

호스팅이 `proc_open` 을 막아 두었으면 7.0.x 의 코어 업데이트 프로그램은 업그레이드 스텝을 별도 프로세스로 실행하지 못하고 멈춥니다. 출력은 다음과 같습니다.

```text
업그레이드 파일 반영은 완료되었으나, 일부 업그레이드 스텝이 현재 프로세스에서 실행될 수 없어 중단되었습니다.
...
나머지 스텝을 적용하려면 아래 명령을 실행하세요 (재다운로드 없이 스텝만 실행):
  php artisan core:execute-upgrade-steps --from=7.0.11 --to=7.1.0 --force
```

파일·`.env` 버전은 이미 7.1.0 이고 유지보수 모드도 풀린 상태지만, 업그레이드 스텝과 **번들 확장 일괄 업데이트는 실행되지 않았습니다.** 다음 순서로 마칩니다.

1. 출력에 나온 `core:execute-upgrade-steps` 명령을 사이트 루트에서 실행합니다(`--from` 은 출력에 나온 값 그대로). 이 명령이 업그레이드 스텝을 실행한 뒤 번들 확장 일괄 업데이트까지 진행합니다.
   - `--force` 를 붙이면 일괄 업데이트를 묻지 않고 레이아웃을 **모두 교체**(overwrite)로 적용합니다. 화면을 고친 사이트는 `--force` 를 빼고 실행해 일괄 업데이트 질문에 답하고 「사용자가 수정한 레이아웃은 보존」을 고릅니다(7.0.x → 7.1.0 은 버전이 달라 `--force` 없이도 스텝이 실행됩니다).
   - sudo(root)로 실행 중이면 출력이 웹서버 계정으로 실행하는 명령(`sudo -u www-data …` 등)을 안내합니다. 안내대로 실행합니다.
2. 이 환경에서는 언어팩 단계도 확장을 갱신한 프로세스 안에서 이어서 돌아, 그 프로세스에 남은 옛 판 확장 설정 때문에 언어팩이 넣는 데이터 번역 일부가 빠질 수 있습니다(예: 쇼핑몰의 새 클레임 사유가 일본어로 비어 있음). 언어팩 명령은 실행할 때마다 새 프로세스로 돌므로, 쓰는 언어팩마다 한 번씩 다시 적용합니다:

   ```bash
   php artisan language-pack:update g7-core-ja --force
   php artisan language-pack:update g7-module-sirsoft-ecommerce-ja --force
   ```

   운영자가 고친 이름은 그대로 둡니다. 식별자 형식은 [일본어 등 언어팩을 쓰는 사이트](#일본어-등-언어팩을-쓰는-사이트)를 봅니다.
3. 결과에 「실패」가 있으면 [건너뛰었거나 실패했을 때](#일괄-업데이트를-건너뛰었거나-일부가-실패했을-때)의 순서대로 조치하고, 마지막에 `php artisan hooks:cache` 를 실행합니다.

## 확장이 업데이트 중 상태로 남았을 때

일괄 업데이트를 실행하는 별도 프로세스가 메모리 부족 등으로 도중에 끝나면, 7.0.x 화면의 일괄 업데이트 결과가 완료로 보여도 그때 업데이트하던 확장이 「업데이트 중」(`updating`) 상태로 남을 수 있습니다. 이 상태의 확장은 꺼진 것으로 취급되어 기능이 동작하지 않고, 기본 사용자 템플릿이 필요로 하는 확장(게시판·이커머스·페이지·다음 우편번호)이면 사용자 화면 전체가 503 오류 화면이 됩니다.

**확인** — 관리자 「모듈 관리」·「플러그인 관리」의 상태 표시, 또는 명령줄에서 상태 칸이 `updating` 인 확장을 찾습니다.

```bash
php artisan module:list
php artisan plugin:list
```

**복구** — 「업데이트 중」 상태는 저절로 풀리지 않고, 이 상태에서는 업데이트 명령도 `--force` 와 관계없이 「진행 중인 작업이 있다」며 거절합니다. 관리 화면에서 상태를 바꾸는 기능도 없습니다. 다음 순서로 복구합니다.

1. 실제로 업데이트가 돌고 있지 않은지 확인합니다(업데이트 명령이 끝나고 10분 이상 지난 뒤 진행). 데이터베이스를 백업합니다.
2. 명령줄 PHP 의 `memory_limit` 를 올립니다([PHP 실행 환경](#php-실행-환경-점검)).
3. 그 확장의 상태만 업데이트 전 상태(대개 `active`)로 되돌립니다. 아래는 이커머스 모듈 예입니다. 플러그인은 `App\Models\Plugin`, 템플릿은 `App\Models\Template` 로 바꿉니다.

   ```bash
   php artisan tinker --execute="App\Models\Module::where('identifier', 'sirsoft-ecommerce')->where('status', 'updating')->update(['status' => 'active']);"
   ```

4. 곧바로 그 확장만 다시 업데이트합니다. 상태를 되돌린 확장은 파일이 일부만 바뀌었을 수 있으므로 `--force` 로 번들 판을 처음부터 다시 적용합니다.

   ```bash
   php artisan module:update sirsoft-ecommerce --source=bundled --force --layout-strategy=keep
   ```

5. 그 확장에 의존하는 플러그인·템플릿·언어팩 가운데 옛 판으로 남은 것이 있으면 [건너뛰었거나 실패했을 때](#일괄-업데이트를-건너뛰었거나-일부가-실패했을-때)의 순서대로 올리고 `php artisan hooks:cache` 를 실행합니다.

## 업데이트 뒤 역할 관리에서 부여할 권한

번들 확장이 새로 선언한 권한은 그 권한을 선언에 적어 둔 역할(관리자·매니저·이커머스 관리자 등)과, 모든 활성 역할에 주도록 선언된 회원용 권한에만 자동으로 붙습니다. **운영자가 직접 만든 역할에는 관리자용 새 권한이 붙지 않습니다.** 업데이트 뒤 관리자 「권한 관리」(`/admin/roles`)에서 역할을 열어 아래 권한을 필요한 역할에 부여합니다.

### 이커머스 1.3.0 의 환불·주문 권한

| 권한 (식별자) | 기본으로 붙는 역할 | 부여하지 않으면 |
| --- | --- | --- |
| 클레임 환불 실행 (`sirsoft-ecommerce.claims.execute-refund`) | 관리자·이커머스 관리자 | 주문 취소 창의 「환불까지 한 번에 처리」가 잠겨 취소하면 환불신청서만 만들어집니다. 클레임 상세의 환불 실행, 나이스페이먼츠 가상계좌 환불, KG이니시스 해외결제(CBT) 환불 재시도가 권한 없음(403)입니다. |
| 클레임 금액 수정 (`sirsoft-ecommerce.claims.update-amounts`) | 관리자·이커머스 관리자 | 클레임의 배송비·차액·환불 예정액을 고칠 수 없습니다(403). |
| 클레임 조회·상태 변경·직권 접수 (`sirsoft-ecommerce.claims.read`·`claims.update-status`·`claims.create`) | 관리자·매니저·이커머스 관리자 | 클레임 목록·상세가 403 이고, 주문 상세의 예상 환불액 조회와 교환·반품·취소·환불 접수가 403 입니다. 7.0.x 에서는 주문 수정 권한으로 하던 일입니다. |
| 주문 삭제 (`sirsoft-ecommerce.orders.delete`) | 관리자 | 주문을 삭제하거나 개인정보 보유기간 「삭제」 방식을 직권 실행할 수 없습니다(403). |

코어 「매니저」 역할은 클레임 조회·접수는 할 수 있지만 환불 실행·금액 수정·주문 삭제 권한은 없습니다. 7.0.x 에서 매니저나 직접 만든 역할에 환불을 맡겨 왔다면(7.0.x 에서는 주문 수정 권한으로 환불까지 할 수 있었습니다) 그 역할에 「클레임 환불 실행」을 부여합니다. 직접 만든 역할에는 위 표의 권한 가운데 맡길 일에 맞는 것을 모두 부여합니다.

같은 판에서 새로 생긴 관리자용 권한 — 문의 조회(`inquiries.read`), 회원 위시리스트·장바구니·배송지 조회와 관리(`wishlists.*`·`carts.*`·`user-addresses.*`) — 도 직접 만든 역할에는 붙지 않습니다.

### 직접 만든 역할에서 바뀐 권한

| 화면 | 7.0.x 에서 쓰던 권한 | 7.1.0 에서 필요한 권한 |
| --- | --- | --- |
| 게시판 환경설정의 본인인증 정책 탭 | 코어 본인인증 정책 조회·수정 (`core.admin.identity.policies.read`·`update`) | 게시판 본인인증 정책 조회·수정 (`sirsoft-board.identity.policies.read`·`update`) — 기본으로는 관리자에게만 붙습니다 |
| 대시보드의 시스템 알림 위젯 | 대시보드 조회 (`core.dashboard.read`) | 시스템 알림 (`core.dashboard.alerts`) — 기본으로는 관리자에게만 붙습니다(매니저에게도 보이려면 부여) |
| 게시판의 스크랩·반응 관리 | (없음) | 게시글 스크랩 관리·반응 관리 (`sirsoft-board.scraps.*`·`reactions.*`) — 조회는 관리자·매니저, 관리는 관리자 |

## 이미 올린 사이트에서 권한 오류(403)가 나면

7.1.0 정식판 이전의 코드로 7.0.x 에서 올린 사이트는, 업데이트 도중 코어 역할·권한 동기화가 실패해 7.1.0 의 새 권한이 어느 역할에도 연결되지 않았을 수 있습니다. 증상은 다음과 같습니다.

- 일반 회원이 마이페이지의 내 정보·활동 기록을 열면 권한 없음(403)
- 관리자가 「방문자 통계」·「회원 알림함」을 열면 권한 없음(403)

사이트 루트에서 아래 명령을 한 번 실행하면 코어 역할·권한·메뉴 선언을 다시 동기화합니다. 운영자가 고친 역할 이름·메뉴 설정은 그대로 두고, 이미 정상인 사이트에서 실행해도 바뀌는 것이 없습니다.

```bash
php artisan core:execute-upgrade-steps --from=7.1.0 --to=7.1.0 --force --skip-migrations --skip-bundled-updates
```

7.1.0 정식판으로 올리는 사이트는 업데이트 과정에서 같은 동기화를 한 번 더 하므로 이 조치가 필요 없습니다. 직접 만든 역할의 403 은 이 명령으로 풀리지 않습니다 — [부여할 권한](#업데이트-뒤-역할-관리에서-부여할-권한)을 확인합니다.

## 일본어 등 언어팩을 쓰는 사이트

업데이트 뒤 새로 생긴 데이터(예: 쇼핑몰의 새 클레임 사유)의 이름이 그 언어로 비어 있으면, 해당 언어팩을 다시 적용합니다. 운영자가 고친 이름은 그대로 둡니다.

```bash
php artisan language-pack:update g7-module-sirsoft-ecommerce-ja --force
```

다른 확장의 언어팩도 같은 형식(`g7-{core|module|plugin|template}-{대상}-{언어}`)으로 실행합니다. 언어팩이 꺼져 있으면(관리자 「언어팩 관리」에서 비활성) 먼저 켜야 반영됩니다.

## 업데이트 뒤 확인

- 관리자 화면: 환경설정·확장 관리·언어팩 관리가 열리는지, 「확장 관리」에 업데이트 표시나 「업데이트 중」 상태로 남은 확장이 없는지.
- 역할: 「권한 관리」에서 계속 쓰는 역할이 켜져 있는지, 매니저·직접 만든 역할로 환불·클레임 처리를 해 보아 권한 없음(403)이 나지 않는지.
- 수정 보존(keep)을 골랐다면: 업데이트 결과에서 「겹쳐서 운영자 것 유지」로 나온 화면의 버튼·기능이 동작하는지.
- 쇼핑몰을 운영한다면: 회원·비회원 주문 상세에서 가상계좌 입금 안내·영수증 버튼이 보이는지, 관리자 주문 목록에 「클레임」 열이 있는지.
- 남은 옛 파일: 이번 업데이트는 7.0.x 배포본과 내용이 같은 남은 번들 파일을 지웁니다. 내용이 달라 남긴 파일은 `storage/logs` 의 업그레이드 로그에 「본문이 7.0.x 배포본과 달라 보존」으로 기록되니, 확인한 뒤 직접 지웁니다.
- 활동 로그: 회원가입·비밀번호 찾기 같은 활동이 기록되는지.
- 사이트 주소: `www` 유무가 다른 주소(예: 사이트 주소가 `www.example.com` 이면 `example.com`)로 접속해 사이트 주소로 이동하는지, `TRUSTED_HOSTS` 에 넣은 별칭 도메인이 열리는지.
