# 7.1.x → 7.2.0 업그레이드 안내

7.1.x 에서 7.2.0 으로 올리는 사이트 운영자와 확장 개발자를 위한 안내입니다. 업데이트 절차는 같고([INSTALL.md 「업그레이드」](../../INSTALL.md#업그레이드)), 이 문서는 **7.2.0 에서 동작이 바뀌어 업데이트 전후에 확인하거나 손볼 것**만 모읍니다. 기능 전체 목록은 [CHANGELOG.md](../../CHANGELOG.md) 의 `[7.2.0]` 절을 봅니다.

## TL;DR (5초 요약)

```text
- 절차는 그대로: 백업 → php artisan core:update (또는 환경설정 > 업데이트 탭) → 번들 확장 일괄 업데이트 승인
- 7.2.0 부터 패키지 서명을 확인한다 — 답할 수 없는 실행(cron·CI·--no-interaction)은 서명 없는 패키지를 --allow-unsigned 없이 받지 않음(--yes·--force 로 대신 안 됨)
- 올려 둔 ZIP 으로 업데이트하면 같은 릴리스의 <zip>.sig.json 도 ZIP 옆에 둔다
- GitHub 설치·업데이트는 태그 릴리스만 받는다(main·master 브랜치를 대신 받지 않음)
- *:refresh-layout 의 기본이 「운영자 수정 유지(keep)」 — 새 판으로 덮으려면 --layout-strategy=overwrite
- core:update 가 업그레이드 스텝 핸드오프로 멈추면 종료 코드 75(재개 필요) — 배포 스크립트가 0 만 성공으로 보면 고친다
- 사이트맵 생성 주기·환율 갱신 시각·GeoIP 갱신 주기는 관리자 > 스케줄 관리로 옮겨짐(바꿔 둔 값은 자동 이전, GEOIP_SCHEDULE_* 는 더 안 씀)
- custom 예약 자리(routes/custom.php·app/Custom·custom/ 등)에 파일을 싣는 패키지나 맞지 않는 custom/composer.json 이 있으면 업데이트가 시작 전에 멈춤
- 레이아웃의 Tailwind 반응형 접두(sm:·md:…)는 폐지 예정 — 직접 고친 레이아웃은 responsive 로 옮긴다(이번 판까지는 그대로 보임)
- 개발자 화면(custom)을 쓰면 7.2.0 이전에 로그인한 회원은 그 화면에서 비회원으로 보인다 — 다시 로그인하면 됨
```

## 순서

1. 데이터베이스와 사이트 파일을 백업합니다([INSTALL.md 「업그레이드 사전 준비」](../../INSTALL.md#업그레이드-사전-준비)).
2. [업데이트 전에 확인할 것](#업데이트-전에-확인할-것)을 봅니다 — 배포 스크립트·예약 명령, custom 예약 자리, 올려 둔 ZIP.
3. `php artisan core:update` 또는 관리자 **환경설정 > 업데이트** 탭으로 올립니다. 번들 확장 일괄 업데이트는 승인합니다.
4. [업데이트 뒤 확인](#업데이트-뒤-확인)을 봅니다.

## 업데이트 전에 확인할 것

### 배포 스크립트·예약 명령 (서명·종료 코드)

7.2.0 은 모듈·플러그인·템플릿·언어팩·코어 패키지를 ZIP 이나 GitHub 로 받을 때 서명(SHA-256 + Ed25519)을 확인합니다. 서명이 틀렸거나 신뢰하지 않는 키로 서명한 패키지는 받지 않고, 서명이 없는 패키지는 한 번 더 확인을 받습니다. 상세는 [확장 패키지 서명](../extension/package-signing.md).

- **답할 수 없는 실행**(cron·CI·`--no-interaction`·예약 작업)에서 서명 없는 패키지를 받으려면 `--allow-unsigned` 를 붙여야 합니다. `--yes` 와 `--force` 는 이 확인을 대신하지 않습니다. 이런 명령을 예약해 두었다면 미리 고칩니다.
- `core:update` 가 업그레이드 스텝 핸드오프로 멈추면 종료 코드가 **0 에서 75(재개 필요)** 로 바뀌었습니다. 배포 스크립트가 0 만 성공으로 본다면 75 를 「재개 필요」로 다루게 고칩니다(종료 코드 표: [cheatsheet](../cheatsheet.md)).
- `module:check-updates`·`plugin:check-updates`·`template:check-updates` 는 GitHub 조회에 실패한 확장이 있으면 실패 표를 출력하고 **종료 1** 입니다. `*:update --source=github` 도 조회 실패면 「업데이트 없음」(0) 대신 종료 1 입니다.
- GitHub 에서 확장을 받을 때 **태그 릴리스만** 받습니다. 릴리스 없이 브랜치만 있는 저장소에서 받던 외부 확장은 「태그 릴리스가 없습니다」로 실패하므로, 제작자에게 릴리스를 요청하거나 ZIP 으로 설치합니다.
- 설치 마법사·요구사항 검사가 PHP `sodium` 확장을 권장 항목으로 확인합니다. 없으면 서명을 검증할 수 없어 서명 없는 패키지와 같이 다룹니다([요구사항](../requirements.md)).

### 올려 둔 ZIP 으로 업데이트할 때

`core:update --zip=` 이나 관리자 화면 「고급 → 직접 올린 ZIP 으로 업데이트」를 쓰면 **같은 릴리스의 서명 파일 `<zip 이름>.sig.json` 을 ZIP 옆에 함께** 올립니다(명령은 `--signature=` 로 경로를 줄 수도 있습니다). 서명 파일이 없으면 미서명 확인을 받고, 환경설정 > 보안 「미서명 패키지 차단」이 켜져 있으면 거부됩니다.

`core:update --source=`(풀어 둔 디렉터리)·`--local` 은 배포 패키지가 아니라 서명 확인 대상이 아닙니다.

### custom 예약 자리와 개발자 패키지

7.2.0 은 개발자가 직접 만든 화면을 두는 예약 자리(`routes/custom.php`·`app/Custom`·`resources/views/custom`·`public/custom`·`lang/custom`·`config/custom.php`·`database/migrations/custom`·`custom/`)를 둡니다. 코어 업데이트는 이 자리를 덮지도 지우지도 않으며, 다음 경우에는 **아무 파일도 바꾸기 전에 멈추고** 사유를 남깁니다.

- 업데이트 패키지에 이 자리의 파일이 들어 있을 때(목록은 `.env` 의 `G7_UPDATE_RESERVED_PATHS` 로 조정)
- `custom/composer.json` 의 개발자 패키지가 새 코어의 패키지와 맞지 않을 때(요구 버전 불만족, 같은 패키지 다른 버전)

7.1.x 에서 이 경로에 파일을 둔 적이 없다면 해당하지 않습니다. 상세는 [개발자 화면 만들기](../custom-development.md).

### 여러 서버가 같은 DB 를 쓰는 구성

검수 서버(`G7_RUNTIME_ROLE=stage`)와 운영 서버가 같은 DB 를 쓰면, 검수 서버를 먼저 올린 뒤 운영 서버의 업데이트가 「업데이트 없음」으로 끝납니다. 이때 운영 서버에서 `php artisan stage:apply-to-live` 를 실행합니다. 한 서버만 스케줄을 돌리려면 나머지 서버에 `G7_SCHEDULER=off` 를 둡니다. 상세는 [실행 역할과 서버별 스케줄 스위치](../backend/runtime-role.md#운영-서버-배포-순서).

## 업데이트하면서 바뀌는 것

### 레이아웃 갱신의 기본값

- `*:refresh-layout`(관리자 [레이아웃 갱신], 개발 대시보드 포함)의 기본이 **운영자 수정 유지(keep)** 로 바뀌었습니다. 종전처럼 새 판으로 덮으려면 `--layout-strategy=overwrite`(API `layout_strategy=overwrite`)를 고릅니다.
- 갱신·확장 업데이트 전에 화면별 판정(유지·새 판 적용·병합·삭제 예정)을 `--dry-run [--json]` 이나 관리자 미리보기로 볼 수 있고, 운영자가 고친 화면을 새 판으로 덮기 직전 그 판을 레이아웃 버전 이력에 남깁니다.
- 코어 업데이트(명령·관리자 화면)의 「레이아웃 처리」 기본값은 종전과 같이 「새 버전으로 덮어쓰기」입니다. 고친 레이아웃이 있으면 시작 화면이 그 개수와 함께 보존을 권합니다.

### 설정 위치가 옮겨진 것

| 항목 | 7.1.x | 7.2.0 | 기존 값 |
| --- | --- | --- | --- |
| 사이트맵 생성 주기·시각 | 환경설정 > SEO | 관리자 > 스케줄 관리 「사이트맵 생성」 | 기본값과 다르게 저장했으면 스케줄로 옮겨짐 |
| 환율 갱신 시각(수출입은행 환율 플러그인) | 플러그인 설정 | 관리자 > 스케줄 관리 | 같은 방식으로 옮겨짐 |
| GeoIP 데이터베이스 갱신 주기 | `.env` `GEOIP_SCHEDULE_FREQUENCY`·`GEOIP_SCHEDULE_TIME` | 관리자 > 스케줄 관리 「GeoIP 데이터베이스 갱신」 | 바꿔 둔 값은 옮겨지고, 환경 변수 줄은 더 쓰이지 않음 |
| 예약 작업 중복 실행 방지 | 켜기/끄기 | 잠금 유지 시간(분, 0 = 끔) | 기존 잠금 시간 그대로 |
| 점검 모드 저장값(`general.maintenance_mode`) | 환경설정 저장값(실제로 읽지 않음) | 삭제 — 점검 모드는 `php artisan down`·`up` | 업그레이드가 지움 |

관리자 화면에서 직접 등록한 예약 작업은 7.1.x 에서 「즉시 실행」으로만 돌았지만, 7.2.0 부터 정해진 주기에 실행됩니다. 업데이트 뒤 스케줄 관리에서 직접 등록한 작업의 주기와 사용 여부를 확인합니다.

### 파일 처리

- **문서 루트 보호 규칙** — 프로젝트 폴더를 문서 루트로 쓰는 배치에서 7.1.x 는 루트 진입 파일만 놓고 보호 규칙(`.htaccess`, IIS `web.config`)을 빠뜨렸습니다. 7.2.0 업데이트가 마무리하며 이번 배포본의 보호 규칙을 놓습니다(이미 있으면 그대로 둡니다).
- **서버 설정 조각(`deploy/`)** — 운영자가 고친 조각은 덮지 않고 새 판본을 `.dist` 로 옆에 둡니다. 합치던 중인 `.dist` 가 있으면 `.dist.new` 로 따로 둡니다.
- **파비콘** — 7.1.x 에서 올리는 이번 업데이트는 이전 판이 파일을 적용해 운영자가 넣은 `public/favicon.ico` 가 한 번 새 기본 아이콘으로 덮이지만, 업데이트가 마무리하며 업데이트 전 백업에서 되살립니다. `--no-backup` 으로 올렸다면 파일을 다시 올립니다. 7.2.0 부터는 환경설정 > 일반 「파비콘」이나 템플릿 설정으로 바꿀 수 있습니다.

### 회원

- 회원 항목(이름·닉네임·휴대폰 등)을 운영자가 정하는 구조로 바뀌었습니다. 업데이트가 종전과 같은 기본값으로 항목을 만들므로, 업데이트 직후 가입 화면·내 정보 수정·검증은 업데이트 전과 같습니다.
- 탈퇴한 회원의 닉네임 접미사가 `_탈퇴` 에서 `_탈퇴_{회원 ID}` 로 바뀌었습니다. 이미 탈퇴한 회원의 닉네임은 바꾸지 않습니다.
- 확장이 만든 역할(이커머스 관리자 등)만 가진 운영자의 관리자 메뉴가 비던 문제가, 7.2.0 업데이트 때 그 역할의 권한으로 열 수 있는 확장 메뉴를 붙이며 해결됩니다. 운영자가 그 역할에서 뺀 메뉴는 다시 붙지 않습니다.
- 회원 상태(차단·탈퇴·휴면·인증 대기)를 모든 API 가 같은 관문에서 다시 봅니다. 로그인한 뒤 차단된 회원은 확장 API 도 쓸 수 없습니다.

### 확장 제거

- 플러그인을 제거할 때 「데이터도 함께 삭제」를 고르지 않으면 관리자 메뉴를 지우지 않습니다(종전에는 일부 플러그인이 옵션과 무관하게 지웠습니다).
- 템플릿을 제거하면 그 템플릿의 레이아웃 첨부·커스텀 번역·미리보기·다른 출처 조각을 함께 지웁니다. 운영자가 고친 데이터는 삭제 직전 활동 로그에 남습니다.

## 7.1.x 기본 템플릿을 복사해 만든 템플릿을 쓰는 사이트

- **로그인·가입 화면** — 소셜 로그인·회사 계정 로그인 단추 자리와 로그인 인계 교환이 없는 옛 화면에는 코어가 화면을 내보낼 때 채웁니다. 템플릿 파일과 저장된 레이아웃은 바꾸지 않습니다([옛 템플릿 호환 심](../extension/layout-extensions.md#옛-템플릿-호환-심-720)).
- **비밀번호 없는 회원** — 옛 화면의 정보 수정 진입·비밀번호 첫 설정 등은 본인인증 창(이메일 인증번호 등)으로 확인을 이어 갑니다.
- **회원 항목** — 회원 항목을 그리지 않는 옛 화면에서 온 요청도 받습니다. 운영자가 추가한 항목을 쓰려면 7.2.0 기본 템플릿의 가입·정보 수정 화면을 참고해 옮깁니다.
- **관리자 템플릿** — 7.1.x 관리자 템플릿을 복사해 쓰면 미서명 확인 단추가 없으므로, 그 화면에서 보낸 설치·업데이트는 7.1 처럼 서명 없는 패키지를 확인 없이 진행하고 서버 로그에 남깁니다. 「미서명 패키지 차단」·서명 불일치·신뢰하지 않는 키는 그대로 막습니다.
- **반응형 클래스** — 레이아웃의 Tailwind 반응형 접두(`sm:`·`md:`·`lg:`·`xl:`·`2xl:`)와 폭에 따라 모양이 바뀌는 의미 클래스(`filter-row`·`grid-2col-responsive`·`page-title` 등)는 폐지 예정입니다. 직접 고친 레이아웃과 사이트 자체 확장이 그대로 보이도록 이 클래스들은 **7.2.0 빌드 CSS 까지 남겨 두고 다음 출시 이후 뺍니다.** 그 전에 엔진 `responsive` 구간 값으로 옮깁니다([반응형 레이아웃](../frontend/responsive-layout.md)).

## 개발자 화면(custom)을 쓰는 사이트

로그인·회원가입·토큰 갱신이 서버 세션과 토큰을 짝지어 두도록 바뀌어, **7.2.0 이전에 로그인한 회원은 개발자 화면에서 비회원으로 보입니다.** 다시 로그인하면 됩니다(그누보드7 화면은 영향 없음).

## 확장 개발자

코어 계약을 직접 구현하거나 옛 형식을 쓰는 확장은 다음을 확인합니다.

- **저장소 계약 추가 메서드** — `MenuRepositoryInterface::deleteMenuPermissions()`, `RoleRepositoryInterface`·`UserRepositoryInterface::deleteMenuPermissions()`, 레이아웃·레이아웃 확장 저장소의 삭제 행 포함 조회 등이 계약에 더해졌습니다. 이 계약을 직접 구현한 클래스는 메서드를 추가하고 시그니처를 맞춥니다(전체 목록은 CHANGELOG `[7.2.0]` Changed 「확장 개발자」).
- **회원 이름** — `findManyByIdsKeyed()` 는 표시 이름 계산에 필요한 칸을 읽고, `getNamesByIds()` 는 원본 이름(없으면 빈 문자열)을 돌려줍니다. 화면에 보일 이름은 표시 이름 계산기로 만듭니다([표시 이름](../extension/display-name.md)).
- **확장 CSS** — 확장 화면은 템플릿 CSS(Tailwind 유틸리티·의미 클래스)에 기대지 않고 자기 CSS 를 싣습니다([확장 CSS 자기 공급](../extension/module-assets.md)).
- **핸들러·이벤트** — 핸들러 이름은 `{식별자}.` 접두로 등록합니다. 콜백 없는 `G7Core.componentEvent.off(name)`·`clear()`, 번호 없는 키로 부르는 `G7Core.websocket.unsubscribe()` 는 폐지 예정입니다([G7Core 고급 API](../frontend/g7core-api-advanced.md)).
- **템플릿 제거 API** — `TemplateService::deleteTemplate()` 와 훅 `core.templates.before_delete`·`after_delete` 는 폐지 예정입니다. 템플릿 제거는 `TemplateManager::uninstallTemplate()` 를 씁니다.
- **스케줄** — `getSchedules()` 를 옛 형식(`name` 없음)에서 새 형식으로 바꾸면 옛 자동 이름의 스케줄을 새 `name` 으로 이어받습니다(명령 문자열이 같을 때). `core.schedule.after_run` 은 실패한 실행에서도 발행되며, 실패만 다루려면 `core.schedule.run_failed` 를 구독합니다([모듈 스케줄](../extension/module-schedules.md)).
- **GitHub 배포** — 확장을 GitHub 로 배포한다면 태그 릴리스를 만들고, 서명 파일(`.sig.json`)을 함께 올립니다([확장 패키지 서명](../extension/package-signing.md)).

## 업데이트 뒤 확인

1. 관리자 **환경설정 > 정보** 에서 버전이 7.2.0 인지 확인합니다.
2. **관리자 > 스케줄 관리** 에서 스케줄러 상태 카드가 「최근 실행」을 보이는지, 직접 등록한 작업의 주기가 맞는지 확인합니다. cron 을 걸 수 없는 호스팅은 **환경설정 > 시스템 > 예약 작업** 의 주소 호출을 설정합니다([INSTALL.md 「스케줄러」](../../INSTALL.md#스케줄러)).
3. 번들 확장 일괄 업데이트 결과에 실패가 없는지 확인합니다. 실패가 있으면 결과가 보여 주는 「다시 실행할 명령」을 실행합니다.
4. 레이아웃을 고친 사이트는 업데이트 결과의 「겹쳐서 운영자 것 유지」 화면과 레이아웃 버전 이력을 확인합니다.
5. `storage/logs/laravel.log` 에 새 오류가 쌓이지 않는지 확인합니다.
